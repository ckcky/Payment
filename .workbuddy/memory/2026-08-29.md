### 从文档确认的现状（权威口径：roadmap.md > technical-solution.md，后者 08-26 已滞后）
- **模块**：根 POM 13 个模块 = 3 个 common（core / dto / mybatis）+ 10 个服务。
- **端口**：merchant 8081、catalog 8082、order 8083、payment 8084、refund 8085、fulfillment 8086、entitlement 8087、reconciliation 8088、settlement 8089、**ledger 8090**。
- **Schema**：MySQL 8 单实例承载 9 个独立 Schema（merchant 无库），Database-per-Service，禁止跨库直查。
- **部署**：10 个服务均为宿主 JVM 进程（无 Dockerfile、未容器化），只有 MySQL / Prometheus(9090) / Grafana(3000) 走 Docker Compose；Prometheus 经 `host.docker.internal` 回抓宿主 8081–8090 的 `/actuator/prometheus`。
- **分层**：编排层（order / payment / refund）→ 执行层（catalog / fulfillment / entitlement）→ 资金层（ledger / reconciliation / settlement / merchant）。依赖单向向内，Ledger 只被依赖，Channel 只依赖外部协议。
- **资金闭环**：事实确认（仅 SUCCEEDED 终态）→ 复式记账 → 对账比对（只产差异、不改原始事实）→ 结算批次（只消费已确认且差异可解释的事实）。UNKNOWN 不记账、不结算。
- **记账映射**（ADR-0011）：支付成功 借 CUSTOMER_CASH A / 贷 MERCHANT_PAYABLE N + PLATFORM_FEE_REVENUE F；退款 借 MERCHANT_PAYABLE R / 贷 CUSTOMER_CASH R；结算 借 MERCHANT_PAYABLE S / 贷 SETTLEMENT_PAYABLE S。Posting 借贷必须平衡，分录 append-only。
- **一致性**：幂等键 + 数据库唯一约束兜底 + 显式状态机 + Saga（禁 2PC/XA），后置 RPC 失败不回滚前序成功事实。金额一律 long 分（ADR-0010 修订：不启用 Money VO）。

- 诊断手段：GlobalExceptionHandler 把未捕获异常吞成 `{"code":"INTERNAL_ERROR","message":"internal error"}`，定位需临时 `printStackTrace` 或看 err 日志（已定位后还原）。
- **根因 1（payment POST 500 DuplicateKeyException）**：`MockChannelAdapter` 每次 JVM 启动 `refGen=new AtomicLong()` 从 1 起，生成 `mock-ref-1` 与历史库残留行撞 `payment_attempts.uk_attempts_channel_reference` 唯一约束。修复：引用加 `runId=UUID.randomUUID().toString().replace("-","").substring(0,12)` 前缀（charge/refund/FAILURE 四生成点），跨重启全局唯一。重建 payment jar 重启。
- **根因 2（order POST 500）**：用户库 `orders` 表缺 `payment_id` 列（`Order.paymentId` 无对应列；规范 `deployment/schema/01-order-schema.sql` 已定义 `payment_id BIGINT NULL`，但用户库是旧 schema 建的）。修复：`ALTER TABLE orders ADD COLUMN payment_id BIGINT NULL` + 重建 order jar 重启后链路转绿。
- 端到端验证（`.workbuddy/tools/demo-chain.ps1`，`upcheck.txt` UP=10/10）：merchant ACTIVE & settlementEligible → catalog SKU SELLABLE → order 自动级联 `paymentGateway.createPayment` SUCCEEDED(totalMinor=2000) → `GET /payments/{id}` SUCCEEDED → ledger `balanced:true, diffByCurrency CNY:0`，双分录 DEBIT acct1(CUSTOMER_CASH) 2000 / CREDIT acct2(MERCHANT_PAYABLE) 2000 (PAYMENT_CAPTURE) → refund SUCCEEDED(500) → reconciliation `matchCount=1, differenceCount=4` 全部 resolved、`unresolvedDifferenceCount=0` → settlement `netMinor=-500, status=UNKNOWN`（设计内终态）。
- **对账/结算说明（重要，非 bug）**：reconciliation 渠道账单是静态 CSV fixture（`reconciliation-service/src/main/resources/fixtures/channel-statements/sample.csv`：mock-ref-1/2、channel-extra-1、refund-1）。真实支付的渠道引用带 runId 前缀，故为 `PLATFORM_ONLY` 差异；`settlementSummary` 仅从 `batch.getMatches()` 派生机实（`ReconciliationApplicationService` L122），所以 income=0、net=-500 是 fixture 驱动的预期表现。重复运行若不清库会累积 PLATFORM_ONLY 差异；`.workbuddy/tools/cleanup.py`（pymysql 截断事务表、保留 ledger.accounts 预设）可复位。
