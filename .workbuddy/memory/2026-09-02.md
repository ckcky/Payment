- **重要纠正（最初结论有误）**：最初压测跑在一个**缓存被关闭（CATALOG_CACHE_ENABLED=false）的 H2 实例**上（环境预设 / 我沿用），读全回源 H2、Redis 无 sku:* 键，于是误判"读缓存未生效 / 应换 MySQL"。改用项目**默认配置（MySQL + 缓存开启 + Redis 可达）**重跑：cache-aside 正常写入 `sku:id:1`，读请求 33,627 次仅 5 次获取 DB 连接（HikariCP acquire=5）→ **DB 卸载 99.98%**；Redis 对服务可达早经 `seckill:sku:1` 递减实测证实，`/actuator/health` 报 redis=DOWN 是健康检查误报（false-negative）。
- 结果：sku_cache_read 33,627 请求 / 549.62 RPS / p95=13.20ms / p99=16.83ms / 错误率 0 → **SLO 全过**；seckill_flash 44,502 请求 / 1,108.2 RPS / p95=415.70ms / p99=434.27ms / 全 200（Lua 配额扣减，配额 1,000,000 极大故未触发 409）→ **延迟 SLO 未达**。
- 秒杀延迟根因：deduct 同步写 MySQL 在 500 VU 下写争用（Redis 本身快、非瓶颈）。MySQL 的 415ms 已优于此前 H2 实例的 886ms，但两者均超 SLO，本质都是"热路径同步写 DB"。
- 产物（持久化于受保护的 .workbuddy，根目录 performance/ 会被目录收口清理）：`.workbuddy/perf/perf-report.html`、`load-result.json`、`loadgen.js`、`generate-report.js`。
- 建议：秒杀热路径去 DB 化（Redis Lua 扣减 + 异步/写-behind 落库）；播种小配额验证 409；修复 Redis 健康检查误报。
