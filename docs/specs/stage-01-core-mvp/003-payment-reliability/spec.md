## User Scenarios & Testing

### User Story 1 - 无回调/超时的支付进入 UNKNOWN 而非猜成败 (Priority: P1)

作为平台，我希望一笔已发起但长时间未收到渠道明确结果的支付，自动从「处理中」收敛为「未知（UNKNOWN）」，而不是被当作成功或失败，从而让资金事实保持可继续收敛的状态，等待查询、后续回调、对账或人工处理。

**Why this priority**: 这是可靠性的基石。超时/断连/不完整响应若被误判为成功或失败，会直接污染资金事实与下游（如错误回写订单为已支付，或错误退款）。先「进未知、不猜成败」是支付系统最核心的正确性保障。

**Independent Test**: 发起一笔支付并让渠道不返回结果（Mock Channel 设为无响应/挂起），超过配置的超时阈值后，验证该支付状态由「处理中」变为「未知」，且订单保持「待支付」、交易不推进为「成功」，并产出 `payment.timeout` 指标与告警信号。

**Acceptance Scenarios**:

1. **Given** 一笔支付处于「处理中」且渠道在超时阈值内无任何明确结果，**When** 超时扫描触发，**Then** 该支付进入「未知」，失败原因记录为超时，订单保持「待支付」、交易保持「处理中/未知」，不触发成功回写。
2. **Given** 一笔支付处于「处理中」但在超时阈值内收到了明确的成功/失败回调，**When** 超时扫描运行，**Then** 该支付因已非「处理中」而被跳过，状态不被覆盖。

---

### User Story 2 - UNKNOWN 通过主动查询/回调收敛为终态，且只触发一次下游动作 (Priority: P1)

作为平台，我希望处于「未知」的支付能通过主动查询渠道状态、或后续渠道回调，被收敛为明确的成功或失败；无论通过哪种途径收敛，对应的订单/交易推进（成功回写）只发生一次。

**Why this priority**: 主链 MVP 已具备 UNKNOWN 收敛能力（`PaymentUnknownResolutionService`），但「谁在何时提供权威结果」这一触发机制尚未建立。没有主动查询，UNKNOWN 只能被动等待渠道回调或依赖对账，资金事实会长期悬空、无法结算。

**Independent Test**: 将一笔支付置为「未知」，由调度器主动调用渠道状态查询并拿到权威成功结果，验证支付收敛为「成功」、订单/交易仅被推进一次（与 002 成功回写一致），且重复查询/重复回调被幂等吸收。

**Acceptance Scenarios**:

1. **Given** 一笔支付处于「未知」，**When** 主动查询调度器从渠道拿到权威成功结果并收敛，**Then** 支付变为「成功」，订单/交易据此推进一次；再次查询同一结果被幂等吸收，不产生第二次下游动作。
2. **Given** 一笔支付处于「未知」，**When** 渠道后续主动回调权威失败结果，**Then** 支付收敛为「失败」，订单保持「待支付」，不触发成功回写。
3. **Given** 渠道在查询中仍返回不明确/挂起，**When** 达到查询尝试上限，**Then** 支付保持「未知」，转入人工收敛或等待对账，不盲目改写状态。

---

### User Story 3 - 有限重试与重试耗尽处理 (Priority: P2)

作为平台，我希望对幂等的渠道调用（如网络超时、渠道临时不可用）进行有限次、带退避的自动重试；非幂等或硬拒绝（如余额不足、卡被拒）不重试；重试耗尽且仍不确定的支付进入「未知」，明确失败的支付进入「失败」。

**Why this priority**: 真实渠道会偶发瞬时故障，盲目重试或无限重试会放大故障、造成重复扣款或雪崩；硬拒绝不应被重试。重试必须有上限与退避，且耗尽后落到可收敛状态而非悬空。

**Independent Test**: 令一次渠道调用因瞬时网络错误失败，验证系统按配置上限（如 3 次）与退避（如 1s/2s/4s）自动重试并最终成功；令一次调用因硬拒绝失败，验证不重试直接进「失败」；令重试全部耗尽且结果不确定，验证进入「未知」并产出 `payment.retry_exhausted` 信号。

**Acceptance Scenarios**:

1. **Given** 一次幂等的渠道调用因瞬时错误失败，**When** 重试调度触发，**Then** 系统在退避间隔后按上限重试，直至成功或耗尽。
2. **Given** 一次渠道调用返回硬拒绝（非瞬时错误），**When** 支付处理，**Then** 支付直接进入「失败」，不发起重试。
3. **Given** 重试次数达到配置上限且结果仍不确定，**When** 最后一次重试结束，**Then** 支付进入「未知」（可被 US2 查询/对账/人工收敛），并产出重试耗尽指标。

### User Story 4 - 人工收敛能力（审计门控） (Priority: P2) — **【本阶段延后 / Deferred，见 ADR-0006】**

作为运营/资金风控人员，我希望对长期「未知」、渠道始终无明确结果、或系统判定存疑的支付，能通过受控的内部端点人工裁定为成功或失败，且每次裁定都必须携带理由并写入资金审计（FINANCIAL_AUDIT），以便事后可追溯、可问责。

**Why this priority**: 自动机制（查询/重试/对账）无法覆盖所有情况（渠道永久失联、结果语义模糊）。人工收敛是 UNKNOWN 的最终兜底路径，但属于高危资金操作，必须有完善的权限与审计约束。

**Independent Test**: 将一笔「未知」支付通过内部受控端点裁定为成功（带理由），验证支付收敛为「成功」、订单/交易据此推进一次，且审计日志包含操作人、理由、前/后状态；对一笔已终态支付发起人工裁定，验证被拒绝/幂等吸收，不产生二次动作。

**Acceptance Scenarios**:

1. **Given** 一笔处于「未知」的支付，**When** 授权人员通过内部端点提交「成功+理由」裁定，**Then** 支付收敛为「成功」、订单/交易推进一次，并写入含操作人/理由/前后状态的资金审计。
2. **Given** 一笔已处于终态（成功/失败）的支付，**When** 收到人工裁定，**Then** 裁定被拒绝或幂等吸收，不覆盖既有终态、不重复推进。
3. **Given** 一笔「未知」支付，**When** 无权限人员或未携带理由发起裁定，**Then** 请求被拒绝，状态不变，不写入成功/失败。

### User Story 5 - 可靠性指标与告警 (Priority: P3)

作为平台 SRE/资金运营，我希望支付可靠性相关的关键事件都有业务指标与审计可追溯：超时数量、重试次数与耗尽次数、UNKNOWN 收敛数量与时长、人工收敛次数，并能对「UNKNOWN 堆积」与「重试耗尽」等业务异常告警，而非只告警基础设施。

**Why this priority**: technical-solution §5/§6 已要求对「支付状态 UNKNOWN 堆积」「重试耗尽」MUST 告警。指标与审计是可靠性的可观测底座，让异常可被及时发现与复盘。

**Independent Test**: 触发一次超时、一次重试耗尽与一次人工收敛，验证分别产出 `payment.timeout`、`payment.retry_exhausted`、`manual.resolution` 等指标，且 UNKNOWN 收敛的真实耗时（从进入未知到收敛）可被度量，相关事件写入资金审计。

**Acceptance Scenarios**:

1. **Given** 发生支付超时/重试耗尽/人工收敛，**When** 事件产生，**Then** 对应业务计数器递增，且事件写入审计。
2. **Given** UNKNOWN 支付数量超过阈值或停留超过阈值时长，**When** 指标采集，**Then** 触发「UNKNOWN 堆积」业务告警。

---

### Edge Cases

- 超时扫描与渠道回调/查询同时到达：以状态机原子迁移 + 乐观锁（version）保证只发生一次状态推进；终态吸收迟到冲突（见 ADR-0007）。
- 乱序回调：先到「失败」后到「成功」时，已终态「失败」吸收迟到「成功」，不覆盖（决策见 ADR-0007）；反之先到「成功」后到「失败」同理吸收。
- 重复收敛（多次查询/多次回调拿到相同权威结果）：幂等吸收，只触发一次下游动作。
- 渠道在查询中返回仍不明确：保持「未知」，不猜测；达到查询尝试上限后停止自动查询，转人工/对账。
- 调度器在单节点下唯一执行；多节点部署时通过数据库行锁/乐观锁保证同一支付同一时刻只被一个调度实例处理（假设：当前单机部署，见 Assumptions）。
- 人工裁定与自动收敛竞争：以乐观锁 + 终态吸收保证不双重推进。
- 重试只对幂等调用生效；硬拒绝不重试，直接进入「失败」。
- UNKNOWN 时长度量：当前 `PaymentUnknownResolutionService` 以 `Duration.ZERO` 记录（领域聚合未携带 updatedAt，属 §8 边界），本 Feature 须在持久化层补全收敛时间戳以产出真实时长（见 plan/data-model）。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 监控处于「处理中」且超过配置超时阈值的支付，并将其推进为「未知（UNKNOWN）」，原因记为超时；推进前状态必须是「处理中」。
- **FR-002**: 超时进入「未知」的支付 MUST NOT 触发订单成功回写或交易成功推进；订单保持「待支付」，交易保持可收敛状态。
- **FR-003**: 系统 MUST 对处于「未知」的支付主动查询渠道状态以获取权威结果，并据此收敛为「成功」或「失败」。
- **FR-004**: 无论通过主动查询还是后续渠道回调收敛，UNKNOWN 支付 MUST 只触发一次下游动作（订单/交易推进），重复结果 MUST 被幂等吸收。
- **FR-005**: 对幂等的渠道调用因瞬时错误失败时，系统 MUST 进行有限次、带退避的自动重试，重试次数与退避 MUST 可通过配置设定且有上限。
- **FR-006**: 对硬拒绝（非瞬时、明确不可重试）的渠道结果，系统 MUST NOT 重试，直接推进为「失败」。
- **FR-007**: 重试耗尽且结果仍不确定的支付 MUST 进入「未知」，可被查询/对账/人工收敛；不得悬空或误判成败。
- **FR-008**: 系统 MUST 提供受控的内部人工收敛端点，允许授权人员将「未知」支付裁定为成功或失败，且 MUST 携带理由并写入资金审计（FINANCIAL_AUDIT，含操作人、前后状态、理由）。
- **FR-009**: 人工收敛 MUST 仅作用于非终态（「未知」）支付；对已终态支付的裁定 MUST 被拒绝或幂等吸收，不覆盖既有状态、不重复推进。
- **FR-010**: 系统 MUST 产出可靠性业务指标：支付超时计数、重试次数、重试耗尽计数、UNKNOWN 收敛计数、UNKNOWN 真实收敛时长、人工收敛计数，并对「UNKNOWN 堆积」与「重试耗尽」告警。
- **FR-011**: 所有状态迁移 MUST 通过支付状态机唯一入口并受乐观锁保护，并发与乱序到达 MUST 不产生重复推进或状态丢失。
- **FR-012**: 跨服务交互（查询/回写/人工后续动作）MUST 沿用既有同步 RPC 与幂等模式，不引入消息队列或分布式事务（遵循 Constitution §4 与 ADR-0001）。

### Key Entities

- **Payment（支付）**: 平台侧支付意图与平台状态。本 Feature 关注其从「处理中→未知→终态」的可靠性迁移，以及支撑迁移的字段（当前尝试次数、最近尝试时间、进入未知时间、收敛时间/操作人）。状态仍由支付领域状态机（已实现对终态冲突的吸收）维护。
- **PaymentAttempt（支付尝试）**: 单次渠道调用的尝试记录（1:N）。本 Feature 关注其尝试序号、结果（成功/瞬时失败/硬拒绝/未知）、重试次数与退避调度依据。
- **ChannelAdapter（渠道适配）**: 已存在的接口与 Mock Channel。本 Feature 复用其「查询状态」能力与「带幂等键的调用」能力，不改变 Payment ≠ Channel 边界（ADR-0001）。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 支付在超时阈值内无明确结果时，100% 进入「未知」而非被误判为成功/失败；订单/交易不被错误推进。
- **SC-002**: UNKNOWN 支付经查询/回调收敛后，订单/交易仅推进一次（与 002 回写一致），重复收敛吸收率 100%。
- **SC-003**: 瞬时错误的渠道调用按配置上限与退避完成重试并最终成功；硬拒绝 0 次重试直接进「失败」；重试耗尽的不确定支付 100% 进入「未知」。
- **SC-004**: 人工收敛对「未知」支付生效且 100% 写入含操作人/理由/前后状态的资金审计；对已终态支付的裁定 100% 被拒绝/吸收。
- **SC-005**: 支付超时、重试耗尽、人工收敛均产出对应业务指标；「UNKNOWN 堆积」与「重试耗尽」可被告警；UNKNOWN 真实收敛时长可被度量。

## Assumptions

- 本 Feature 不引入消息队列、分布式事务或跨服务异步事件；自动收敛通过进程内调度器（Scheduler）驱动，沿用同步 RPC 与幂等（Constitution §4、ADR-0001）。
- 当前为单节点/单机部署，调度器单实例运行；多节点下的分布式调度锁作为后续演进，不在本 Feature 范围（如需，另立 ADR）。
- 渠道「查询状态」能力在 Mock Channel 中可模拟（返回成功/失败/仍不明确），真实渠道对接不在本 Feature 范围。
- 人工收敛端点为内部/受控端点（运营与资金风控使用），其鉴权与访问控制在当前阶段沿用既有安全基线（详见 ADR-0006），完整生产级权限体系在 Phase 9（Risk/Security）统一建设。
- 重试/超时/查询的默认阈值（如超时 30s、重试上限 3、退避 1s/2s/4s、查询尝试上限 5）为合理默认值，可通过配置覆盖；具体取值在 plan/research 中给出并可在实施后按需调优。
- 本 Feature 复用并补强既有能力：UNKNOWN 收敛（`PaymentUnknownResolutionService`）、支付状态机终态吸收、002 成功回写，不重复实现已有部分。
