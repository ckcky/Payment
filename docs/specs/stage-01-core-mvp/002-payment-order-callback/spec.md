# Feature Specification: 支付成功回写订单与交易状态

**Feature Branch**: `002-payment-order-callback`

**Created**: 2026-08-27

**Status**: Draft

**Input**: User description: 打通「支付成功 → 订单/交易」的状态回写闭环。当一笔支付被明确确认为成功时，订单与交易通过回调感知支付成功，分别推进到「已支付」和「成功」，消除当前「支付已成功但订单仍待支付、交易仍处理中」的一致性问题；重复回调幂等吸收。

## User Scenarios & Testing

### User Story 1 - 支付成功后订单与交易同步推进 (Priority: P1)

作为平台业务方，我希望当一笔支付被明确确认为成功时，对应的订单和交易能够同步推进到「已支付 / 成功」状态，而不是停留在「待支付 / 处理中」，从而保证订单、交易、支付三者的业务事实一致。

**Why this priority**: 这是当前主链路的缺口——支付已成功但订单仍待支付、交易仍处理中，导致订单状态失真，并让后续履约、退款、对账所依赖的订单前提错误。它是资金与交易一致性的核心。

**Independent Test**: 创建一笔订单并发起支付，令支付明确成功，验证订单状态从「待支付」推进为「已支付」、已支付金额等于订单金额、交易状态从「处理中」推进为「成功」，且订单与交易的状态均由各自领域规则驱动。

**Acceptance Scenarios**:

1. **Given** 订单处于「待支付」且交易处于「处理中」，支付已明确成功，**When** 订单侧收到该笔支付成功的事实，**Then** 订单推进为「已支付」，已支付金额等于订单金额，交易推进为「成功」。
2. **Given** 支付已成功但订单已处于「已取消」或「已关闭」等非法前态，**When** 收到支付成功事实，**Then** 订单不被推进，该异常被记录以供人工/对账处理，不伪造订单已支付。

---

### User Story 2 - 重复回调幂等且不重复累加 (Priority: P2)

作为平台业务方，我希望同一笔支付的支付成功事实即使重复到达，也不会造成订单重复累加已支付金额、重复推进状态或产生重复业务动作，系统返回与首次一致的结果。

**Why this priority**: 回调与通知天然可能重复、乱序、延迟到达，资金正确性要求重复吸收；这是「资金入口幂等」原则在回写链路上的直接体现。

**Independent Test**: 对已因某笔支付进入「已支付」的订单，重复发送同一笔支付的支付成功事实，验证订单状态、已支付金额、交易状态均不变化，且返回当前状态而非报错或二次累加。

**Acceptance Scenarios**:

1. **Given** 订单已因支付 A 进入「已支付」，**When** 支付 A 的支付成功事实再次到达，**Then** 订单状态与已支付金额保持不变，交易状态保持不变，返回当前状态，不二次累加。
2. **Given** 同一笔支付成功事实触发下游履约/权益动作，**When** 该事实重复到达，**Then** 下游依据订单号等业务身份幂等吸收，不重复创建履约或权益。

---

### User Story 3 - 仅明确成功才回写，失败/未知不回写 (Priority: P3)

作为平台业务方，我希望只有当支付被明确确认为成功时，才触发订单与交易的成功推进；支付失败或结果未知时，订单保持「待支付」、交易保持其「处理中/未知」状态等待后续收敛，不得猜测成败。

**Why this priority**: 这是支付系统最核心的正确性保障（未知不等于失败），同时明确本 Feature 的边界是「成功回写」而非「失败/未知回写」。

**Independent Test**: 分别令支付进入「失败」和「未知」，验证订单不被标记为「已支付」、交易不被标记为「成功」；对未知结果，验证订单/交易停留在可继续收敛的状态。

**Acceptance Scenarios**:

1. **Given** 支付明确失败，**When** 平台处理该结果，**Then** 订单保持「待支付」，交易按业务规则推进为「失败」或保持可重试状态，不触发成功回写。
2. **Given** 支付结果未知（渠道超时/不确定），**When** 平台处理该结果，**Then** 订单保持「待支付」，交易保持「处理中」或「未知」，等待查询/回调/对账收敛，不猜测成功。

---

### Edge Cases

- 支付成功回写与订单「已取消/已关闭/已履约」等状态冲突时，拒绝推进并记录异常，不伪造成功。
- 重复回调、乱序回调、延迟回调到达时，靠业务身份与状态幂等吸收。
- 回写失败（订单侧不可用/超时）时，支付成功事实保留，订单/交易等待重试或人工收敛，不回写支付为失败。
- 支付成功事实无论通过立即返回、渠道回调、还是查询收敛得知，下游动作都只发生一次。

## Requirements

### Functional Requirements

- **FR-001**: 当一笔支付被明确确认为成功时，系统 MUST 将对应订单从「待支付」推进到「已支付」（整单支付，不支持部分支付），已支付金额置为订单金额，并记录下游支付单号（paymentId）。
- **FR-002**: 当一笔支付被明确确认为成功时，系统 MUST 将对应交易推进为「成功」。
- **FR-003**: 订单/交易的成功推进 MUST 由各自领域的状态机规则驱动，其他领域只能通过业务事实触发，不得直接修改对方状态或数据。
- **FR-004**: 支付成功事实的重复到达 MUST 被幂等吸收：已推进到终态的订单/交易在重复回调时保持不变，不重复累加已支付金额，返回当前状态。
- **FR-005**: 幂等 MUST 依据订单号、支付号等业务身份与当前状态判断；重复的支付成功事实不得产生额外的业务动作。
- **FR-006**: 只有明确支付成功才触发成功回写；支付失败或结果未知 MUST NOT 触发订单/交易的成功推进。
- **FR-007**: 无论支付成功是通过立即返回、渠道回调还是后续查询收敛得知，系统 MUST 产生一致且只一次的下游动作，不因获知途径不同而产生差异或重复。
- **FR-008**: 回写失败时，支付成功事实 MUST 保留，订单/交易 MUST 可通过重试、查询或人工收敛推进，不得将支付回写为失败。
- **FR-009**: 订单处于非法前态（如已取消/已关闭）时，系统 MUST 拒绝推进并记录异常，不伪造成功。
- **FR-010**: 支付成功回写订单/交易 MUST NOT 阻塞或依赖履约、权益的同步完成。

### Key Entities

- **Order（订单）**: 承载订单状态与已支付金额；本 Feature 关注其从「待支付」到「已支付」的推进（整单支付，不支持部分支付），以及下游支付单号（paymentId）的记录。状态与金额仍由订单领域自身维护。
- **Transaction（交易）**: 承载商业交易生命周期状态；本 Feature 关注其从「处理中/未知」到「成功」的推进。
- **Payment（支付）**: 支付成功事实的来源；其「成功」状态是触发本 Feature 回写的唯一业务事实。支付状态仍由支付领域自身维护。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 支付成功后，订单从「待支付」推进到「已支付」，已支付金额等于订单金额，完成率 100%。
- **SC-002**: 同一笔支付的支付成功事实重复到达多次时，订单状态与已支付金额仅推进一次，不产生重复累加。
- **SC-003**: 支付失败或未知时，订单与交易不被标记为「已支付/成功」，正确性 100%。
- **SC-004**: 回写失败时，支付成功事实可被追踪，并能经重试或人工收敛最终达成一致，不出现「支付成功但订单永久停留待支付」且无收敛路径的情况。

## Assumptions

- 不支持部分支付：一次支付 = 一笔全额支付，支付成功将订单整单置为已支付，已支付金额等于订单金额。
- 幂等依据订单号、支付号等业务身份与当前状态实现，不新增独立的去重表或去重机制（已在方案中确认）。
- 本 Feature 只覆盖「支付成功」这一事实的回写；支付失败/未知的处理与收敛沿用既有支付状态机与对账能力，不在本 Feature 范围内。
- 履约、权益等下游已具备基于订单号等业务身份的幂等，重复通知不产生重复动作。
- 跨服务交互沿用既有的同步 RPC 模式，不引入消息队列或分布式事务。
