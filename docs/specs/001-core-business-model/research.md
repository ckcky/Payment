# 研究记录：Commerce & Payment Platform MVP

## 决策 1：运行形态采用独立微服务

- **决策**：使用多个独立服务，服务使用不同端口；单机阶段可共用物理数据库但使用独立 Schema。
- **理由**：项目负责人明确要求服务从自身视角独立，单机只是一种部署方式，不改变服务边界。
- **备选方案**：模块化单体。未采用，因为它与当前已有服务结构和独立部署目标不一致。

## 决策 2：Payment Channel 与 PaymentAttempt 保持在 Payment 模块内部

- **决策**：Channel 是 Payment 的适配能力，PaymentAttempt 是 Payment 的一次外部交互事实。
- **理由**：Payment 保存平台意图和平台状态，Attempt 保存每次渠道尝试；这样能表达重试、重复回调和 UNKNOWN，而不制造过早的独立服务。
- **备选方案**：Channel 独立领域/服务。未采用，因为渠道尚无独立业务生命周期，独立化会扩大协调面。

## 决策 3：MVP 固定核心基数

- **决策**：`Order 1:1 Transaction`、`Transaction 1:1 Payment`、`Payment 1:N PaymentAttempt`。
- **理由**：兼顾模型清晰和未来扩展；支付重试属于 Attempt，不制造多个 Payment 意图。
- **备选方案**：一个 Order 直接关联多个 Payment。暂不采用，避免把分期、组合支付和拆单责任混入首个闭环。

## 决策 4：UNKNOWN 是独立业务状态

- **决策**：渠道超时、连接中断或结果不完整进入 UNKNOWN，经查询、回调、对账或人工处理收敛。
- **理由**：未知不等于失败；猜测会造成重复扣款或错误履约，是支付正确性的核心风险。
- **备选方案**：超时直接失败。拒绝，因为无法证明渠道是否已经完成资金动作。

## 决策 5：同步 RPC 用于跨服务协作

- **决策**：Payment 成功通过同步 RPC 请求履约，履约完成后通过同步 RPC 请求权益授予；退款后处理、对账和结算也通过公开 RPC 协作。
- **理由**：服务仍保持独立边界，同时避免 MVP 为异步通信引入 MQ 和额外运维复杂度。
- **备选方案**：跨服务异步事件。暂不采用，因为当前业务规模和部署目标不需要 MQ；未来如有真实需求再单独立项。

## 决策 6：Ledger 暂不实现但明确限制

- **决策**：MVP 不建立 Ledger 模型、不执行真实资金划转；支付、退款、结算只验证业务事实和状态闭环。
- **理由**：需求明确将 Ledger 延后，同时 Constitution 禁止绕过 Ledger 进行真实资金变动。边界必须在 Plan 中明确，避免模拟逻辑被误认为生产资金路径。
- **备选方案**：先实现简化余额或简化账本。拒绝，因为简化账本容易形成错误的资金模型并扩大本阶段范围。

## 决策 7：可观测性先满足业务可见性

- **决策**：记录关联 ID、状态变化、关键业务计数和 UNKNOWN/差异/失败事件；Trace 保留接口边界，重量级观测基础设施延期。
- **理由**：MVP 首先需要回答“发生了什么、卡在哪里、是否重复”，而不是建设完整平台。
- **备选方案**：首先建设完整分布式观测平台。拒绝，当前单体没有对应的跨服务运维收益。
