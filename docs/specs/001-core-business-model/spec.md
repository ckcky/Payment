# Feature Specification: Commerce & Payment Platform 核心业务模型

**Feature Branch**: `001-core-business-model`

**Created**: 2026-08-26

**Status**: Draft

**Input**: User description: 建立 Commerce & Payment Platform 的核心业务模型，明确领域职责、实体、状态、关系、同步/异步边界、数据所有权、一致性、幂等和异常场景；当前只讨论业务和领域模型，不讨论具体技术实现。

## User Scenarios & Testing

### User Story 1 - 完成商品购买生命周期 (Priority: P1)

作为平台业务方，我希望能够从用户购买商品开始，经过订单、交易、支付、履约和权益发放，形成一条边界清晰、可追踪的完整业务生命周期。

**Why this priority**: 这是平台最核心的业务主链路，其他领域模型都需要围绕它协作或提供约束。

**Independent Test**: 使用一个可购买商品和一个用户，走通“选择商品 → 创建订单 → 创建交易 → 发起支付 → 渠道返回结果 → 支付成功 → 履约 → 权益发放”，并能够分别查看每个领域的实体、状态和责任；重复支付请求、重复渠道通知和渠道未知结果不得造成重复业务动作。

**Acceptance Scenarios**:

1. **Given** 商品和 SKU 可销售，**When** 用户提交购买，**Then** 平台创建订单及订单明细，并冻结本次购买所依据的商品、SKU、数量和价格快照。
2. **Given** 订单满足支付条件，**When** 用户发起支付，**Then** 平台创建独立的交易和支付记录，支付记录引用订单/交易但不替代它们。
3. **Given** 支付请求已提交渠道，**When** 渠道明确返回成功，**Then** 支付进入成功状态并触发后续履约，不要求权益在同一次同步请求中完成。
4. **Given** 支付渠道超时或返回无法确认的结果，**When** 平台处理该结果，**Then** 支付保持待确认/未知状态，不得直接当作成功或失败入账。
5. **Given** 同一幂等请求或同一渠道通知重复到达，**When** 平台再次处理，**Then** 返回与首次处理一致的业务结果，且不重复创建支付、履约或权益动作。

### User Story 2 - 支持退款生命周期 (Priority: P2)

作为平台业务方，我希望退款是一个独立的业务决策和生命周期，能够协调支付退款、履约/权益处理及后续对账，而不是简单调用一次渠道退款。

**Why this priority**: 退款同时影响资金、订单履约和用户权益，必须在主链路边界明确后建模。

**Independent Test**: 对已支付订单提出部分或全部退款，能够看到退款申请、支付退款、履约/权益处理和对账之间的独立状态；重复退款请求不造成重复退款。

**Acceptance Scenarios**:

1. **Given** 订单存在可退款金额，**When** 用户提出退款，**Then** 平台创建退款记录，记录退款金额、原因、关联订单和支付，并校验累计退款不超过可退款金额。
2. **Given** 退款需要渠道执行，**When** 渠道明确退款成功，**Then** 退款资金结果被记录，并触发履约/权益处理和对账流程。
3. **Given** 渠道退款结果未知，**When** 平台处理超时或不确定结果，**Then** 退款保持待确认/未知状态，不得重复发起不可确认的资金动作。
4. **Given** 同一退款幂等键重复提交，**When** 平台再次处理，**Then** 返回原退款结果或当前状态，不产生第二笔退款。

### User Story 3 - 建立对账与结算链路 (Priority: P3)

作为商户或财务人员，我希望平台能够把支付和退款结果与外部渠道记录进行核对，并基于已确认的财务数据形成结算，而不是把对账和结算混为一个动作。

**Why this priority**: 对账和结算是资金闭环的后置能力，依赖支付、退款和商户结算信息已经具备明确边界。

**Independent Test**: 提供一组平台记录和渠道记录，能够识别一致、金额不一致、状态不一致、平台有而渠道无、渠道有而平台无等差异，并仅对满足结算条件的数据生成结算批次。

**Acceptance Scenarios**:

1. **Given** 某周期存在平台支付、退款和渠道记录，**When** 执行对账，**Then** 平台生成对账结果和差异记录，不直接修改原始支付或退款事实。
2. **Given** 对账发现差异，**When** 财务人员处理差异，**Then** 差异拥有独立处理状态和处理依据，原始业务记录保持可追溯。
3. **Given** 财务数据已达到结算条件，**When** 生成结算，**Then** 平台创建结算批次，记录商户、周期、金额、扣减项和结算状态。
4. **Given** 结算请求重复提交或结算结果未知，**When** 平台再次处理，**Then** 通过结算幂等约束避免重复结算，并保留待确认状态。

### Edge Cases

- SKU 在下单后价格、名称或销售状态发生变化时，订单使用创建时的快照，不追溯修改历史订单。
- 一个订单可能对应多次支付尝试，但同一支付意图不得因重复请求产生重复资金动作。
- 支付成功、履约失败或权益发放失败可以分别存在，不能把它们压缩成一个状态。
- 渠道回调可能重复、乱序、延迟到达或签名有效但内容与当前支付状态冲突。
- 渠道超时不代表支付失败；平台无法确认时必须进入未知状态并等待查询、后续通知、对账或人工处理。
- 订单取消、部分退款、全部退款和已履约状态之间可能存在业务冲突，必须依据可退款金额和履约/权益可撤销性判断。
- 部分退款、多次退款的累计金额不得超过已支付且尚未退款金额。
- 对账可能发现重复记录、金额差异、币种差异、状态差异和时间窗口差异。
- 结算不能基于未确认的支付、退款或未处理的重大对账差异。
- 任一跨服务步骤失败时，前序事实不得被删除或伪装成未发生；后续步骤应可通过 RPC 重试、查询或人工处理。

## Domain Model Overview

### Domain Responsibilities, Entities and States

| 领域 | 解决的问题 | 不负责的问题 | 核心实体 | 核心状态 |
|---|---|---|---|---|
| Merchant | 谁可以经营商品、接收交易并参与结算 | 不负责订单、支付执行、履约或对账差异 | Merchant、Settlement Account | 待审核 → 有效 → 暂停/终止 |
| Product | 面向用户和商家的商品概念与商品生命周期 | 不负责具体销售价格快照、订单或支付 | Product、Product Version | 草稿 → 上架 → 下架 → 归档 |
| SKU | 哪个具体销售单元可以被购买、以什么属性交付 | 不负责订单金额最终确认或支付状态 | SKU、Price、Delivery Definition | 草稿 → 可售 → 暂停 → 失效 |
| Order | 用户买什么、向谁买、订单金额和购买生命周期 | 不负责渠道协议、资金收取或直接发放权益 | Order、Order Item、Price Snapshot | 待确认 → 待支付 → 部分支付/已支付 → 履约中 → 已完成/已取消/已关闭 |
| Transaction | 一次商业交易如何关联订单和支付，以及交易是否完成 | 不负责渠道通信、履约交付或权益管理 | Transaction、Transaction Relation | 待处理 → 处理中 → 成功/失败/取消/未知 |
| Payment | 一次资金收取意图和支付尝试的生命周期 | 不负责商品、订单履约和具体渠道协议 | Payment、Payment Attempt、Payment Result | 待支付 → 处理中 → 成功/失败/已关闭/未知 |
| Payment Channel | 如何与外部支付机构交互并解释其结果 | 不负责平台订单、履约、权益或最终业务判断 | Channel、Channel Attempt、Channel Reference | 可用 → 不可用/停用；渠道尝试待处理 → 已受理 → 成功/失败/未知 |
| Refund | 为什么退、退多少、是否可退以及退款整体进度 | 不负责单独替代支付退款、履约撤销或对账 | Refund、Refund Item、Refund Decision | 申请中 → 处理中 → 成功/部分成功/失败/未知/拒绝/关闭 |
| Fulfillment | 如何交付商品或服务，以及交付是否完成 | 不负责支付结果确认或权益内部生命周期 | Fulfillment、Fulfillment Item、Delivery | 待履约 → 履约中 → 已交付/部分交付/失败/取消 |
| Entitlement | 用户获得什么消费权利、如何使用和撤销 | 不负责判断用户是否已付款或渠道退款 | Entitlement、Grant、Consumption | 待授予 → 可用 → 部分使用/已用尽 → 已过期/已撤销/失败 |
| Reconciliation | 平台事实与外部事实是否一致，差异如何处理 | 不负责资金划转或修改原始交易事实 | Reconciliation Batch、Match、Difference | 待处理 → 对账中 → 一致/有差异/处理中/已关闭 |
| Settlement | 商户在指定周期应结算多少以及批次是否完成 | 不负责发现全部原始差异或代替支付成功判断 | Settlement Batch、Settlement Item、Adjustment | 待结算 → 计算中 → 待执行 → 执行中 → 成功/失败/未知/关闭 |

### Core State Transitions

状态转换由领域自身负责，其他领域只能通过业务事实触发转换，不能直接修改状态。

| 业务链路 | 允许的关键转换 | 触发条件和边界 |
|---|---|---|
| 商品销售 | Product 上架 → SKU 可售 → SKU 暂停/失效 | 只有可售 SKU 才能进入订单；已创建订单使用价格和商品快照 |
| 订单 | 待确认 → 待支付 → 部分支付/已支付 → 履约中 → 已完成 | 取消和关闭必须满足未支付或业务允许的条件；不得因履约失败回写为支付失败 |
| 交易 | 待处理 → 处理中 → 成功/失败/取消/未知 | 交易结果由关联支付事实和业务规则决定；未知不可直接收敛为成功或失败 |
| 支付 | 待支付 → 处理中 → 成功/失败/未知 → 已关闭 | 渠道明确结果才能进入成功/失败；超时、断连和不完整响应进入未知 |
| 支付尝试 | 待处理 → 已受理 → 成功/失败/未知 | 每次尝试有独立渠道引用；重复通知只幂等更新同一尝试 |
| 履约 | 待履约 → 履约中 → 已交付/部分交付/失败 | Payment Success 只触发履约，不决定履约最终状态 |
| 权益 | 待授予 → 可用 → 部分使用/已用尽 → 过期/撤销 | 只有履约或其他合法权益来源确认后才能授予；授予失败不抹掉支付事实 |
| 退款 | 申请中 → 处理中 → 成功/部分成功/失败/未知 | 可退款金额由已支付金额减累计退款和业务扣减共同约束 |
| 对账 | 待处理 → 对账中 → 一致/有差异 → 处理中/已关闭 | 对账只产生匹配或差异事实，不修改原始支付/退款事实 |
| 结算 | 待结算 → 计算中 → 待执行 → 执行中 → 成功/失败/未知 | 只能使用已确认且满足结算条件的数据；未知结果不得重复执行 |

## Domain Relationships and Interaction Boundaries

### Business Relationships

- Merchant 拥有与平台之间的商业合作关系，并被 Product、Order、Reconciliation 和 Settlement 引用。
- Product 包含或分组 SKU；SKU 是可购买、可交付的单元，被 Order Item 引用。
- Order 包含 Order Item 和 Price Snapshot；一个 Order 可以有一个或多个 Transaction 和 Payment Attempt。
- Transaction 连接商业购买与一个或多个 Payment 记录，但不取代二者的生命周期。
- Payment 通过渠道引用使用 Payment Channel；渠道结果成为 Payment 的输入，而不是直接更新 Order。
- Payment Success 产生触发 Fulfillment 的业务事实；Fulfillment 可能创建或请求 Entitlement 授权。
- Refund 引用原始 Order 和 Payment，并可能触发支付冲正、履约撤销和权益吊销。
- Reconciliation 将已确认的 Payment/Refund 事实与外部记录进行比较，并产生 Difference 记录。
- Settlement 消费已确认的财务事实以及已解决或显式接受的调整项；不消费未确认的支付结果。

### Synchronous RPC Boundaries

同步交互仅限于调用方需要立即得到的判断：

- Product/SKU → Order：校验所选 SKU 是否可购买，并获取创建订单所需的数据。
- Order → Transaction/Payment：请求创建或受理一个支付意图，并接收其初始状态。
- Payment → Payment Channel：在有即时响应可用时，提交渠道尝试或查询已知的渠道引用。
- Refund → Order/Payment：在受理退款请求前，校验退款资格并获取当前可退款金额。
- Client/Operations → Order/Payment/Refund/Entitlement/Reconciliation/Settlement：查询当前状态和业务历史。

任何同步边界都不得要求 Payment 等待 Fulfillment 或 Entitlement 完成，也不得要求 Reconciliation 等待 Settlement 执行。

### Internal Event and Cross-Service RPC Boundaries

跨服务不使用异步事件，跨领域副作用通过同步 HTTP/RPC 用例完成。服务内部可以使用事件记录本地状态变化，但这些事件不跨服务发布：

- `OrderConfirmed` 或 `OrderReadyForPayment` 在 Order 与 Payment 之间通过 RPC 触发交易/支付处理。
- `PaymentSucceeded`、`PaymentFailed` 和 `PaymentUnknown` 作为 Payment 服务内部事实，并通过 RPC 驱动下游用例。
- `FulfillmentRequested`、`FulfillmentCompleted` 和 `FulfillmentFailed` 作为 Fulfillment 服务内部事实，并通过 RPC 驱动履约与权益决策。
- `EntitlementGranted`、`EntitlementRevoked` 和 `EntitlementGrantFailed` 作为 Entitlement 服务内部事实，提供消费权利结果。
- `RefundAccepted`、`RefundSucceeded`、`RefundUnknown` 和 `RefundFailed` 通过 RPC 驱动后续履约/权益处理和对账。
- `ReconciliationCompleted` 和 `ReconciliationDifferenceFound` 通过 RPC 告知结算资格和差异处理。
- `SettlementCreated`、`SettlementSucceeded`、`SettlementUnknown` 和 `SettlementFailed` 作为 Settlement 服务内部事实，报告结算生命周期。

服务内部事件表示已发生的事实或明确的业务命令。跨服务通过公开 RPC 用例传递请求和结果；任何 RPC 或内部事件都不授予写入另一个领域内部数据的权限。

### Data Ownership

| 领域 | 唯一事实来源 |
|---|---|
| Merchant | 商户身份、经营状态和结算资格 |
| Product / SKU | 商品定义、销售单元、价格/交付定义 |
| Order | 订单、订单明细、价格快照和订单状态 |
| Transaction | 商业交易关系和交易状态 |
| Payment / Payment Channel | 支付意图、支付尝试、平台支付结果和渠道交互引用 |
| Refund | 退款申请、退款决策、退款金额和退款状态 |
| Fulfillment | 交付任务、交付结果和履约状态 |
| Entitlement | 权益授予、使用、撤销和有效期 |
| Reconciliation | 对账批次、匹配结果和差异处理状态 |
| Settlement | 结算批次、计算结果、调整项和结算状态 |

其他领域只能保存必要的引用或不可变业务事实副本，不能把副本当作原领域的可修改事实来源。

### Consistency and Idempotency Rules

- 每个领域内部的实体状态、关键金额和关联事实必须在同一业务操作中保持一致。
- 跨领域流程采用最终一致；每个异步步骤必须具备可重试、可补偿、可查询或人工收敛路径。
- 支付、退款和结算的幂等键必须与业务作用域绑定；同一键重复提交返回同一业务结果或当前状态。
- 渠道通知和业务事件按“可能重复、乱序、延迟”设计；消费方依据事件身份、业务幂等键和当前状态吸收重复事件。
- 金额、币种和累计金额校验必须在支付、退款、对账和结算边界分别执行，不能只依赖上游校验。
- UNKNOWN 是需要后续收敛的业务状态，不是失败的别名；在未知状态收敛前不得重复执行不可确认的资金动作。

### Major Exception Scenarios

| 异常 | 业务处理原则 |
|---|---|
| SKU 不可售或价格失效 | 拒绝创建订单或要求重新确认，不使用过期销售条件 |
| 订单不可支付或重复支付 | 拒绝新的不合法支付；相同幂等请求返回原支付结果 |
| 渠道超时/未知 | Payment 或 Refund 进入 UNKNOWN，等待查询、通知、对账或人工处理 |
| 重复/乱序回调 | 按渠道交易引用和支付尝试幂等处理，不回退已确认的合法状态 |
| 支付成功但履约失败 | 保留支付成功，单独重试或人工处理履约，不将支付改为失败 |
| 履约完成但权益失败 | 保留履约事实，重试或人工补发权益，不重复扣款 |
| 退款金额超过可退金额 | 拒绝超额退款，保留拒绝原因和当前累计金额 |
| 退款成功但权益无法撤销 | 保留退款事实，建立权益异常处理，不伪造撤销成功 |
| 对账金额/状态不一致 | 创建差异并保留原始事实，禁止静默改写支付或退款 |
| 结算数据未确认或结算结果未知 | 暂停该批次或进入 UNKNOWN，禁止重复结算 |

## Requirements

### 1. 领域职责与边界

- **FR-001**: 系统 MUST 将 Merchant、Product、SKU、Order、Transaction、Payment、Payment Channel、Refund、Fulfillment、Entitlement、Reconciliation、Settlement 作为可独立说明职责和生命周期的业务领域概念。
- **FR-002**: Merchant MUST 负责商户身份、经营主体和结算相关基础信息；MUST NOT 负责订单履约、支付渠道协议或账务差异处理。
- **FR-003**: Product MUST 负责面向业务的商品定义；SKU MUST 负责可销售、可定价和可交付的具体销售单元。Product MUST NOT 直接承担订单或支付状态。
- **FR-004**: Order MUST 负责购买意图、商品明细、价格快照、订单金额和订单生命周期；MUST NOT 负责支付渠道细节或直接发放权益。
- **FR-005**: Transaction MUST 负责一次商业交易与订单、支付之间的关联及交易生命周期；MUST NOT 取代订单或支付的独立状态。
- **FR-006**: Payment MUST 负责资金收取意图、支付尝试、支付状态、幂等和支付结果；MUST NOT 依赖具体渠道协议。
- **FR-007**: Payment Channel MUST 负责外部支付机构的协议适配、请求/响应转换、通知和渠道特有错误；MUST NOT 决定平台订单、履约或权益状态。
- **FR-008**: Refund MUST 负责退款申请、退款金额、退款决策和退款生命周期；MUST NOT 被建模为单一的“调用渠道退款”动作。
- **FR-009**: Fulfillment MUST 负责商品或服务交付；Entitlement MUST 负责用户可消费的权益及其授予、使用、撤销和有效期。支付成功 MUST NOT 等价于权益已发放。
- **FR-010**: Reconciliation MUST 负责比较平台事实与渠道/外部事实、发现和处理差异；Settlement MUST 负责基于已确认数据形成商户结算批次。二者 MUST 保持独立。

### 2. 核心实体与状态

- **FR-011**: 系统 MUST 为每个核心实体定义唯一标识、创建时间、来源和关联关系，并保留关键业务事实的历史可追溯性。
- **FR-012**: Merchant 核心实体 MUST 至少包括商户身份、经营状态、结算账户引用和结算资格信息；核心状态至少包括待审核、有效、暂停、终止。
- **FR-013**: Product 核心实体 MUST 至少包括商品身份、商品类型、展示信息和商品状态；SKU MUST 至少包括 SKU 身份、所属商品、销售属性、价格引用、可售状态和交付信息。
- **FR-014**: Order 核心实体 MUST 至少包括用户、商户、订单明细、金额快照、币种、已支付金额、已退款金额和订单状态；订单状态 MUST 至少支持待确认、待支付、部分支付、已支付、履约中、已完成、已取消、已关闭。
- **FR-015**: Transaction 核心实体 MUST 至少包括交易身份、订单引用、交易金额、交易目的和交易状态；交易状态 MUST 能表达待处理、处理中、成功、失败、取消和未知。
- **FR-016**: Payment 核心实体 MUST 至少包括支付身份、交易引用、支付意图、支付金额、币种、支付尝试、幂等键、渠道引用和支付状态；支付状态 MUST 能表达待支付、处理中、成功、失败、已关闭和未知。
- **FR-017**: Payment Channel 核心实体或配置概念 MUST 至少包括渠道身份、支持的支付方式、渠道状态和渠道交易引用；不得把渠道状态直接当作平台支付状态。
- **FR-018**: Refund 核心实体 MUST 至少包括退款身份、订单/支付引用、退款金额、原因、退款幂等键和退款状态；退款状态 MUST 能表达申请中、处理中、成功、部分成功、失败、未知、拒绝和关闭。
- **FR-019**: Fulfillment 核心实体 MUST 至少包括履约身份、订单/明细引用、交付内容和履约状态；Entitlement 核心实体 MUST 至少包括权益身份、用户、来源、有效期、可用额度/范围和权益状态。
- **FR-020**: Reconciliation 核心实体 MUST 至少包括对账周期、数据来源、对账批次、匹配结果和差异记录；Settlement 核心实体 MUST 至少包括商户、结算周期、结算批次、收入、退款、费用/调整项、应结金额和结算状态。

### 3. 状态转换与业务链路

- **FR-021**: 每个具有生命周期的核心实体 MUST 通过明确的、受约束的状态转换规则变更状态，不得允许任意跳转。
- **FR-022**: 主链路 MUST 支持：商品/SKU 可售 → 创建订单 → 创建交易 → 发起支付 → 支付尝试 → 渠道处理 → 支付成功 → 触发履约 → 履约完成或失败 → 授予/拒绝权益 → 用户消费。
- **FR-023**: Order、Transaction、Payment、Fulfillment 和 Entitlement 的状态 MUST 独立维护；一个领域的成功只能触发另一个领域的动作，不能直接伪造另一个领域的最终状态。
- **FR-024**: 支付成功 MUST 触发履约流程；履约或权益处理失败时，系统 MUST 保留支付成功事实并记录后续失败，不得回写成支付失败。
- **FR-025**: 退款链路 MUST 支持：退款申请 → 退款资格判断 → 支付退款 → 履约/权益处理 → 对账；退款处理不得绕过原支付关系和退款累计金额约束。
- **FR-026**: 资金链路 MUST 支持：已确认支付/退款事实 → 对账 → 差异处理 → 达到结算条件 → 生成结算批次；对账不得直接等同于结算。

### 4. 同步、异步、所有权与一致性

- **FR-027**: 同步调用 MUST 只用于需要立即得到判断或结果的前置校验、订单创建、支付受理、退款受理和查询；不得要求一次同步调用完成跨领域的全部后置流程。
- **FR-028**: 跨服务副作用 MUST 通过公开的同步 HTTP/RPC 用例完成；当前不得引入 MQ 或跨服务异步事件。
- **FR-029**: 服务内部事件 MUST 表达已经发生的业务事实或明确的业务命令；跨服务接收方 MUST 依据自身领域规则处理 RPC 请求，不得直接共享或修改发送方内部实体。
- **FR-030**: 每个领域 MUST 拥有自己核心实体和数据的唯一事实来源；其他领域只能通过公开的业务关系或事实交互使用，不得直接修改其内部数据。
- **FR-031**: 单一领域内部必须保证状态和关键事实的一致性；跨领域 RPC 流程 MUST 允许最终一致，并提供超时、幂等重试、补偿、查询、对账或人工收敛路径。
- **FR-032**: 支付、退款和结算等资金动作 MUST 保持金额、币种、关联关系和业务事实可追溯；不得因重复事件产生重复资金动作。

### 5. 幂等与异常

- **FR-033**: 支付、退款、结算入口 MUST 要求调用方提供幂等键，并根据业务范围保证同一幂等键只产生一个业务结果。
- **FR-034**: 渠道通知、查询结果和跨服务 RPC 请求 MUST 支持重复、延迟和超时；重复处理不得重复创建实体、授予权益或执行资金动作。
- **FR-035**: 只有能够证明安全幂等的外部操作才允许重试；重试必须有次数/时间上限，并在耗尽后进入可处理的异常状态。
- **FR-036**: 支付或退款超时、渠道不可用、网络中断或响应不完整时，系统 MUST 进入未知/待确认状态，不得猜测成功或失败。
- **FR-037**: 非法状态转换、金额超限、币种不一致、订单不可支付、重复退款和商户不可结算 MUST 被拒绝并保留明确原因。
- **FR-038**: 对账差异、履约失败、权益授予失败、支付未知堆积和结算失败 MUST 可被独立追踪、重试、补偿或人工处理。

## Domain Model Alternatives

### 方案 A：按业务能力拆分（当前基准方案）

Merchant、Catalog（Product/SKU）、Order/Transaction、Payment/Channel、Refund、Fulfillment、Entitlement、Reconciliation、Settlement 分别建模；Ledger 作为资金基础领域在后续资金设计中补充。

- 优点：职责清晰，符合各领域独立生命周期；支付、履约、权益、对账和结算可以分别演进。
- 缺点：跨领域协作多，需要严格维护关系、事件和最终一致。
- 适用：希望建立生产级 Commerce & Payment Platform 的完整学习模型。

### 方案 B：按交易主链路合并

将 Product/SKU 合并为 Catalog，将 Order/Transaction 合并为 Trading，将 Fulfillment/Entitlement 合并为 Delivery，将 Payment/Channel/Refund 合并为 Payment Operations。

- 优点：早期模型较少，端到端流程容易理解，跨领域协调成本较低。
- 缺点：支付与渠道、履约与权益、退款与支付退款的边界容易被抹平；后续拆分成本高。
- 适用：只做小规模交易原型或只验证主流程时。

### 方案 C：以资金为中心建模

以 Payment、Refund、Reconciliation、Settlement 为核心，Order、Fulfillment、Entitlement 作为外围业务能力。

- 优点：资金状态、对账和结算优先级高，适合收单或纯支付平台。
- 缺点：商品、订单、履约和权益的商业生命周期表达不足，不适合作为完整 Commerce 平台的第一版模型。
- 适用：平台主要价值是支付基础设施而非商品交易闭环时。

本 Feature 不替用户最终批准方案。方案 A 作为后续 Plan 的工作基线；若选择方案 B 或 C，必须重新评估领域边界、状态机、数据所有权和事件关系。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 评审人员能够仅依据本文档画出商品购买、退款、支付对账结算三条业务链路，并正确区分每个领域的职责，完成率达到 100%。
- **SC-002**: 12 个核心领域均有明确的“负责什么 / 不负责什么”、核心实体和核心状态，缺失项为 0。
- **SC-003**: 主链路至少覆盖正常成功、渠道失败、渠道未知、重复请求、重复通知、履约失败和权益失败 7 类场景，并为每类场景定义状态或处理原则。
- **SC-004**: 对账和结算能够被独立描述和验收，文档中不存在“对账即结算”或“支付成功即权益发放”的等价关系。
- **SC-005**: 后续实现人员能够根据本文档识别每个核心实体的数据所有者、同步边界和异步边界，无需引入具体技术实现才能理解业务规则。
- **SC-006**: 本阶段不产生代码、数据库结构或具体基础设施方案；所有内容保持在业务和领域模型范围内。

## Assumptions

- 第一阶段面向平台核心业务模型，不定义具体用户界面、渠道品牌、支付方式、地区合规规则或商户行业差异。
- Product 与 SKU 分开建模：Product 是商品概念，SKU 是可销售单元；实际服务是否合并属于后续架构决策。
- Transaction 单独保留：它表达商业交易关系和交易生命周期，不与 Order 或 Payment 互相替代。
- Payment Channel 作为支付领域中的独立概念讨论，不在本阶段决定它是否独立部署。
- 退款默认支持部分退款和多次退款，但累计退款不得超过可退款金额。
- 用户消费发生在权益被授予且处于可用状态之后；支付成功本身不赋予消费权。
- 本阶段使用“支付事实”和“退款事实”描述资金业务，不定义具体账本实现；任何真实资金变动仍须遵守项目宪法的资金正确性要求。
- 对领域合并或拆分没有默认永久承诺，方案 A 仅作为后续设计的起点。
