## ADR-0003: UNKNOWN 收敛触发机制

- **状态**：**Accepted**（2026-08-28 负责人确认）
- **日期**：2026-08-28
- **决策者**：人类（项目 Owner）
- **关联 Feature**：`003-payment-reliability`（spec US2 / FR-003 / FR-004）

### Context（背景）

既有 `PaymentUnknownResolutionService.resolve(paymentId, ChannelResult)` 只**消费**外部传入的权威结果并将其收敛为终态，但项目里**没有任何机制主动产生这个权威结果**。结果是：一笔支付进入 UNKNOWN 后，只能被动等待渠道后续回调，或依赖周期性对账才能收敛。在渠道不回调、对账周期长的情况下，资金事实会长期悬空、无法结算，直接违反 `technical-solution.md` §4.4「UNKNOWN 不猜成败、靠查询/对账/人工收敛」的原则。

需要决定：**谁、何时、以何种方式**为 UNKNOWN 支付提供权威结果。

### Decision（决策）

采用「**主动查询调度器 + 人工收敛端点**」双路径，而非被动等待回调：

1. **主动查询调度器**：周期性扫描处于 `UNKNOWN` 的支付，调用渠道适配器的「状态查询」能力获取权威结果（`ChannelResult`），再喂给既有 `PaymentUnknownResolutionService.resolve` 收敛。查询须基于幂等键，重复查询不得产生副作用。
2. **人工收敛端点**：授权人员可将长期 UNKNOWN 裁定为成功/失败（详见 ADR-0006）。
3. **后续渠道回调**：仍可被 `resolve` 吸收，与现有链路兼容（同一支付只收敛一次）。
4. **查询尝试上限**：达到配置上限（默认 5 次）渠道仍返回不明确时，停止自动查询，保持 `UNKNOWN`，转人工收敛或等待对账。

### 备选方案

- **A. 仅被动等待渠道回调**：实现简单，但渠道不回调则永久悬空，结算被阻塞（否决）。
- **B. 仅依赖对账收敛**：无需查询能力，但实时性差、结算延迟高（否决）。
- **C. 主动查询 + 人工收敛（采纳）**：及时收敛、结算不被阻塞，且保留人工兜底。

### Consequences（后果）

**正面**：UNKNOWN 可被及时、可靠地收敛；结算不再因悬空事实被阻塞；与既有 `resolve` 能力无缝衔接。

**代价**：需要渠道「查询状态」能力（Mock Channel 可模拟）；引入调度器与查询尝试计数；必须保证渠道查询接口幂等，避免重复查询造成副作用。

### 关联

- ADR-0001（同步 RPC、当前无 MQ）
- `docs/architecture/technical-solution.md` §4.3.2 / §4.4
- `003-payment-reliability` spec：US2、FR-003、FR-004

## ADR-0004: 超时进入 UNKNOWN 的策略

- **状态**：**Accepted**（2026-08-28 负责人确认）
- **日期**：2026-08-28
- **决策者**：人类（项目 Owner）
- **关联 Feature**：`003-payment-reliability`（spec US1 / FR-001 / FR-002）

### Context（背景）

支付发起后，渠道可能超时、断连或返回不完整响应。当前项目没有把「处理中（PROCESSING）」推进到「未知（UNKNOWN）」的超时机制，导致这类支付永远停在 PROCESSING，订单/交易无从收敛，也无法被对账纳入差异识别。`technical-solution.md` §4.4 明确要求「超时 ≠ 失败/成功，进入未知状态」。需要决定**由谁触发、阈值如何、默认值多少、与状态机如何衔接**。

### Decision（决策）

1. **触发者**：由支付服务内的**进程内调度器（Scheduler）**周期性扫描「处于 PROCESSING 且距最近一次尝试超过阈值」的支付，统一将其收敛为 UNKNOWN。不在 RPC 调用方处各自标记，保持领域状态变更唯一入口。
2. **作用范围**：仅作用于 `PROCESSING`（PENDING 必须先经 `start()`；已终态不处理）。
3. **阈值可配置**：超时阈值按渠道 SLA 配置；**默认 30s**（Mock/同步场景的合理值，真实渠道上线时按 SLA 调整）。调度扫描间隔可配置，默认 10s。
4. **不猜成败**：进入 UNKNOWN 时原因记为「超时」，订单保持「待支付」、交易保持可收敛状态，**绝不**触发成功回写（沿用 002 边界）。

### 备选方案

- **A. 依赖 RPC 客户端超时即在调用方标记 UNKNOWN**：调用方与领域耦合，状态机入口被绕过（否决）。
- **B. 仅人工/对账处理超时**：实时性差，PROCESSING 长期堆积（否决）。
- **C. 领域侧调度器统一超时收敛（采纳）**：状态机唯一入口、阈值可配置、与重试/查询调度一致。

### Consequences（后果）

**正面**：超时确定进未知、不猜成败，对齐 `technical-solution` §4.4；PROCESSING 不再永久堆积。

**代价**：阈值需按渠道调优——过小会误判进行中的支付为 UNKNOWN，过大会延迟收敛；调度器需幂等（同一支付同一时刻只处理一次）。

### 关联

- ADR-0003（UNKNOWN 后续收敛路径）
- `003-payment-reliability` spec：US1、FR-001、FR-002
- `docs/architecture/technical-solution.md` §4.4（超时/UNKNOWN 原则）

## ADR-0005: 支付重试模型

- **状态**：**Accepted**（2026-08-28 负责人确认）
- **日期**：2026-08-28
- **决策者**：人类（项目 Owner）
- **关联 Feature**：`003-payment-reliability`（spec US3 / FR-005 ~ FR-007）

### Context（背景）

真实渠道会偶发瞬时故障（网络超时、临时不可用）。`technical-solution.md` §4.4 规定：「仅对幂等的外部调用允许自动重试，须有退避与上限；非幂等调用禁止盲目重试」。当前项目没有重试机制，一次瞬时失败就直接落到失败，且缺乏对「硬拒绝 vs 瞬时错误」的区分。需要决定**重试位置、上限、退避、以及耗尽后的去向**。

### Decision（决策）

1. **重试资格**：仅对**幂等**的外部调用（同一幂等键可安全重放）允许自动重试。**硬拒绝**（明确不可重试，如余额不足、卡被拒、参数错误）**不重试**，直接 `FAILED`。
2. **重试位置**：由支付服务内的**进程内调度器**驱动（**非**同步内联循环），通过 `PaymentAttempt` 记录尝试序号与结果；复用渠道适配器的「带幂等键调用」能力进行重放。不引入 MQ（遵循 ADR-0001）。
3. **上限与退避**：重试次数可配置，**默认 3 次**（首次 + 2 次重试）；退避指数 **1s / 2s / 4s**（可配置、设上限，避免雪崩）。
4. **耗尽策略**：
   - 耗尽且仍**不确定**（超时/网络）→ `markUnknown`，进入 ADR-0003 的收敛路径。
   - 明确**失败** → `FAILED`。
   - 任一路径都不盲重试非幂等调用，也不重复扣款。

### 备选方案

- **A. 同步内联重试**：阻塞调用线程、无弹性退避、易放大故障（否决）。
- **B. MQ 重试队列**：超出当前架构（ADR-0001 当前无 MQ），增加运维负担（否决，留待 Phase 10 评估）。
- **C. 调度器驱动 + 幂等重放 + 指数退避（采纳）**：瞬时故障自愈、不雪崩、不重复扣款，且复用既有幂等键与状态机。

### Consequences（后果）

**正面**：瞬时故障可自愈；硬拒绝快速失败；耗尽后落到可收敛的 UNKNOWN 而非悬空；与 Constitution §4 / ADR-0001 一致。

**代价**：需要在 `PaymentAttempt` 记录重试次数与最近尝试时间；调度器须幂等；阈值需按渠道调优。

### 关联

- ADR-0001（当前无 MQ、同步 RPC）
- Constitution §4（幂等 / 状态机 / 重试 / UNKNOWN）
- `003-payment-reliability` spec：US3、FR-005 ~ FR-007

## ADR-0006: 人工收敛能力与权限/审计约束 —— **本阶段不做（Not Implemented）**

- **状态**：**Not Implemented / Deferred**（2026-08-28 负责人决定：本 Feature 不实现，延后至 Phase 9 Risk/Security）
- **日期**：2026-08-28
- **决策者**：人类（项目 Owner）
- **关联 Feature**：`003-payment-reliability`（spec US4 / FR-008 / FR-009）

### Context（背景）

自动机制（主动查询、重试、对账）无法覆盖所有情况：渠道永久失联、结果语义模糊、或系统判定存疑时，UNKNOWN 支付需要一条**最终兜底**路径。`technical-solution.md` §4.3.2 将「人工处理」列为 UNKNOWN 收敛路径之一。需要决定：**是否提供人工收敛端点、其能力边界如何、权限与审计约束是什么**。这属于 Constitution §8 人类决策边界相关的高危资金操作。

### Decision（决策：本阶段不实现）

**本 Feature（Phase 3 · Payment Reliability）不包含人工收敛端点。** 理由：

1. 人工收敛属于高危资金操作，需配套完整的权限/审计体系，而该体系在路线图 Phase 9（Risk / Security）统一建设，本阶段不重复搭基建。
2. 本阶段的「主动查询 + 超时进 UNKNOWN + 有限重试」已覆盖绝大多数 UNKNOWN 的自动收敛；剩余无法自动收敛的 UNKNOWN，先保持 UNKNOWN 状态、依赖既有对账流程与后续 Phase 9 的人工能力兜底，**不阻塞本 Feature 交付**。
3. 收敛的「终态冲突策略」（迟到成功不覆盖已失败，ADR-0007）不受本决策影响——即使未来实现人工收敛，也须受终态吸收约束。

> 原方案（供 Phase 9 参考）：受控内部端点 `POST /internal/payments/{id}/resolve`，仅允许将 UNKNOWN 裁定为成功/失败，MUST 携带理由并写入 `FINANCIAL_AUDIT`，仅作用于 UNKNOWN，复用既有 `resolve` 保证只一次下游。

### 备选方案

- **A. 无人工收敛，全靠对账**：运营无法及时干预，UNKNOWN 只能等对账周期（本阶段采纳此简化，因 Phase 9 将补齐）。
- **B. 本阶段即实现受控端点 + 强制审计**：可及时干预，但权限体系未就绪，易留缺口（否决，延后至 Phase 9）。
- **C. 人工可直接改写任意状态**：绕过状态机、审计缺失、极易滥用（否决）。

### Consequences（后果）

**正面**：本 Feature 范围收敛、可按期交付；不引入半成品的权限/审计；与 Phase 9 建设节奏一致。

**代价**：少量长期 UNKNOWN 在本阶段只能靠对账兜底，无法由运营即时裁定；这是有意的、与路线图一致的取舍。

### 关联

- ADR-0003（UNKNOWN 收敛路径之一，自动部分已实现）
- ADR-0007（终态冲突策略：人工裁定亦受终态吸收约束）
- `003-payment-reliability` spec：US4、FR-008、FR-009（本阶段标记为 Deferred）
- 路线图 `docs/architecture/roadmap.md` Phase 9 · Risk / Security

## ADR-0007: 终态冲突策略（迟到成功不覆盖已失败支付）

- **状态**：**Accepted**（2026-08-28 负责人确认）
- **日期**：2026-08-28
- **决策者**：人类（项目 Owner）
- **关联 Feature**：`003-payment-reliability`（spec Edge Cases / FR-011）

### Context（背景）

渠道回调或主动查询结果可能**乱序**到达：例如先收到「失败」、后收到「成功」，或反之。需要决定：**已经处于终态「失败（FAILED）」的支付，是否可以被后到的「成功」结果覆盖？** 这与资金正确性、以及后续退款/结算的前提直接相关，是可靠性设计中最容易出错的歧义点。

### Decision（决策）

**不覆盖。** 维持现有支付状态机的不变量——终态（`SUCCEEDED` / `FAILED` / `CLOSED`）吸收一切迟到的冲突结果（返回 `false`，不触发任何下游事件）：

- 先 `FAILURE` 后 `SUCCESS` → 支付**保持 FAILED**。
- 先 `SUCCESS` 后 `FAILURE` → 支付**保持 SUCCEEDED**（对称）。

若怀疑「失败」为误判（如渠道返回语义歧义、或断连期间的临时错误被当成失败），**不自动覆盖**，而是经**后续对账**显式修正，且必须写入审计。失败即被视为可信终态。（注：原方案中的「人工收敛」路径已被 ADR-0006 决定本阶段不做，故误判修正统一走对账。）

### 备选方案

- **A. 迟到成功覆盖已失败**：看似「修复」误判，但信任不可靠的迟到结果，违反「失败即终态」；更严重的是，若该支付已被退款/结算，翻转为成功会造成账实混乱（否决）。
- **B. 维持终态吸收（采纳，与既有 `Payment.java` 实现一致）**：状态机简单、可预测、无幽灵翻转；误判走对账显式纠正。

### Consequences（后果）

**正面**：状态机可预测、无意外翻转；与既有 `Payment.java` 终态吸收实现一致；避免「已退款/已结算资金被错误翻转为成功」的灾难。

**代价**：确有失败误判时不能自动纠正，必须走对账——这是有意的、可问责的取舍，而非缺陷。

### 关联

- `payment-service/.../domain/Payment.java`（状态机终态吸收）
- ADR-0006（人工收敛是误判的显式修正路径，本阶段延后）
- `003-payment-reliability` spec：Edge Cases、FR-011
