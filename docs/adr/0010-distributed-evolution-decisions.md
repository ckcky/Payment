> **本阶段的核心立场**：Roadmap Phase 10 明确写着「不因『看起来像微服务』而默认引入 Service Mesh、Kubernetes、CQRS 或 Event Sourcing」，且前置条件是「至少一个真实业务瓶颈或隔离需求；拆分方案和运维成本获得负责人确认」。因此本阶段的**最简实现不是去拆服务，而是先把「按证据演进」的门禁立起来**：边界测试 + 运行手册 + 拆分提案模板。任何一次真实拆分都必须带着填好的提案走评审。

> Constitution §8（人类决策边界）：服务边界、领域边界、数据库 Schema 变更属 MUST 由人确认的范畴。本集合的 ADR 即为该确认的载体。

## ADR-0029 本期不做任何服务拆分，先立「可拆分性」门禁

**状态**：✅ Accepted（2026-08-30 裁决「保持现状」）

**背景**：Phase 10 是长期演进终点，不是一次性交付项。当前 10 个服务已经物理分模块、按 Schema 隔离数据、只经 HTTP/Feign 通信，具备被独立部署的**结构条件**；但没有任何真实业务瓶颈或隔离需求的证据。

**决策（最简）**：本期**不拆分任何服务、不引入任何新基础设施**，改为把「服务能被独立拆出去」的前提固化为构建期门禁：
- 新增 `architecture-tests` 模块（唯一职责：结构校验，无业务代码、不被任何服务依赖），用 ArchUnit 强制四条不变量：
  1. 服务之间零编译期耦合（跨服务只能走 HTTP/Feign + `common-dto`）；
  2. `domain..` 不依赖 Spring / MyBatis / `infra..`（领域框架无关）；
  3. `api..` / `web..` 不直达 `infra.persistence..`（接入层必经应用服务）；
  4. 不得出现 MQ、JTA/XA 等分布式基础设施依赖。
- 配套一条**防空转门禁**：结构上四条规则全是否定式断言，若目录导入失败会「0 个类 → 全绿」。故先断言每个服务导入的类数 > 5，否则规则空转即视为失败。

**理由**：这四条一旦被破坏，服务就不再可能独立演进；在破坏发生的当次提交就失败，比真要拆分时才发现「早就耦合死了」便宜几个数量级。

**影响**：新增第 14 个 Maven 模块 `architecture-tests`（`maven.install.skip`，不产出可部署构件），必须排在 `<modules>` 最后——它按目录导入各服务的 `target/classes`（各服务是 `spring-boot-maven-plugin` 重打包的可执行 jar，类在 `BOOT-INF/classes`，不能作为普通依赖被 import）。

**待确认**：门禁是否要升级为「阻断合并」；是否要把四条不变量写进 Constitution 作为强制项。

## ADR-0030 独立数据库迁移：先定触发条件，不动手

**状态**：✅ Accepted（2026-08-30 裁决「保持现状」；本期不迁）

**背景**：当前「数据库按服务使用独立 Schema」，但全部 Schema 跑在同一个 MySQL 实例上（同一台机器、同一个物理库）。这是当前原则允许的——服务可以独立部署，但可以运行在同一台服务器和同一个物理数据库上。

**决策（最简）**：**现在不迁**。只登记触发条件，任一条成立才启动迁移评估：
- **容量**：单实例 CPU 持续 > 70% 或 连接数长期 > 最大连接数 70%，且垂直扩容已到性价比拐点。
- **隔离**：某服务的慢查询 / 锁等待 / 大批量任务（如结算跑批、对账扫描）实质性影响其它服务的 P99。
- **合规 / 归属**：某服务的数据需要独立的备份策略、 retention 或访问控制边界（如账本 `ledger`）。
- **可用性**：某服务需要独立的主从切换或跨可用区部署，而共享实例无法满足 RTO/RPO。

**迁移顺序建议（届时按证据选，不预设）**：`ledger-service` 最优先——它是资金事实的最终来源、写入模式最稳定、且合规隔离诉求最强；其次是 `reconciliation-service` 与 `settlement-service`（跑批型负载，最容易拖垮共享实例）。

**回滚方案（每次迁移 MUST 具备）**：双写期保留旧实例为权威；按 Schema 粒度切流，单个 Schema 回滚不影响其它；回滚判据与窗口在提案中写明。

**待确认**：触发阈值是否合理；`ledger` 是否需要独立的备份 retention 策略。

## ADR-0031 跨服务异步消息：只在有明确证据时才评估

**状态**：⛔ Not Implemented（不做）—— 2026-08-30 裁决「**不使用 MQ**」；判据保留，未达证据前不评估

**背景**：当前跨服务一致性靠「幂等 + 状态机 + 主动查询收敛 + Saga（下游失败不回滚资金事实）+ 对账兜底」实现，同步 HTTP/Feign 是唯一通信方式，无 MQ、无 2PC/XA。

**决策（最简）**：**继续不用 MQ**。引入前必须先有下面任一类证据：
- **性能证据**：同步链路的 P99 受串行 RPC 拖累，且已证明「异步化」是唯一可行解（先试超时/熔断/批量/缓存）。
- **解耦证据**：某下游必须是「尽力而为」的扇出（fan-out）且允许最终一致，同步调用导致上游可用性被下游绑架。
- **削峰证据**：存在明确的突发写流量，同步路径无法承载。

**约束（即使将来引入也 MUST 遵守）**：MQ 只用于**通知与解耦**，不得承载资金事实的唯一真相；账本仍以 `ledger-service` 的 DB 为准；消息消费端 MUST 幂等；跨服务仍不引入 2PC/XA。

**影响**：构建期已有规则禁止 MQ / JTA-XA 依赖出现（ADR-0029 规则 4），将来若评估通过需先修订本 ADR 与那条规则。

**待确认**：是否接受「先做超时/熔断/批量」作为引入 MQ 前的必过步骤；是否需要对账链路先行异步化。

## ADR-0032 独立扩缩容与故障隔离：按关键等级分级，而非一刀切

**状态**：✅ Accepted（2026-08-30 裁决「忽略」= 保持现状）

**背景**：服务已经可以独立部署，但「哪些该先独立扩容、哪些该先做隔离」没有统一口径，容易变成按直觉堆基础设施。

**决策（最简）**：建立**关键等级（criticality tier）**作为扩缩容与隔离投入的排序依据（只登记分级，本期不改任何部署形态）：

| 等级 | 服务 | 定位 | 扩缩容/隔离优先级 |
| --- | --- | --- | --- |
| T0 资金事实 | `ledger-service` | 记账唯一真相，写入不可丢 | 最高：独立实例 + 独立备份 |
| T1 交易主链 | `payment-service`、`order-service` | 直接影响成交 | 高：优先独立扩容、优先熔断保护 |
| T1 资金闭环 | `refund-service`、`settlement-service`、`reconciliation-service` | 资金正确性依赖，允许短时延迟 | 中：跑批错峰，必要时独立 |
| T2 履约/权益 | `fulfillment-service`、`entitlement-service` | 下游副作用，允许重试与最终一致 | 中低：跟随 T1 扩 |
| T3 主数据 | `merchant-service`、`catalog-service` | 读多写少 | 低：可缓存前置 |

**已有的隔离手段（无需新组件）**：出站 RPC 显式超时（connect 1s / read 1s，渠道 HTTP 1.5s）、Resilience4j 熔断、重试仅对幂等 sink、幂等键兜底重复、终态吸收乱序结果。

**待确认**：分级是否被认可；是否需要为 T0 单独定义 RTO/RPO 指标。

## ADR-0033 拆分提案模板与运行手册：每次拆分的准入门禁

**状态**：✅ Accepted（2026-08-30 裁决「忽略」= 保持现状）

**背景**：Phase 10 验收标准要求「每次拆分都有问题、收益、成本和回滚方案；业务事实和契约向后兼容；服务边界测试和运行手册齐全」。

**决策（最简）**：把门禁落成两个可直接填写/查阅的文档，本期即补齐：
- `docs/operations/split-proposal-template.md` —— 拆分提案模板，四段必填：**问题（证据）→ 收益 → 成本（含运维成本）→ 回滚方案**。缺任一段不予评审。
- `docs/operations/runbook.md` —— 运行手册：10 个服务的端口、依赖、健康检查、关键指标、常见故障与处置、回滚步骤；以及必要的环境变量清单（含 Phase 9 引入的 `PAYMENT_ADMIN_TOKEN` / `PAYMENT_INTERNAL_TOKEN` / `PAYMENT_CHANNEL_SECRET`）。

**契约兼容性要求**：任何拆分 MUST 保证现有跨服务契约（`common-dto` 的 RPC DTO）向后兼容；破坏性变更走新端点 + 双轨期，不得就地改语义。

**待确认**：运行手册的维护责任人；提案是否需要附带压测数据基线。
