# Payment Platform v2.0.0

> 发布日期：2026-09-16 ｜ 上一版本：[v1.0.0](https://github.com/ckcky/Payment/releases/tag/v1.0.0)（2026-09-07）
> 版本跨度：124 个提交 ｜ 6 个 spec 落地（018 / 019 / 020 / 021 / 022 / 023 / 026）+ 2 个 spec 立项（027 / 028）

v2.0.0 是**运行形态与质量体系**的一次整体升级：平台首次支持**容器模式一键起栈**（与宿主模式双轨并存），
同时补齐了**全链路自动化测试体系**——资金正确性不再只靠人工点演示页验证，而是有 9 条不变量断言进 CI 守门。
退款链路重构为 order 驱动的两层退款单，并打通渠道退款异步回调闭环。

---

## 亮点

- **容器模式（双轨并存）**：新增 `deployment/start-container.sh`，与宿主模式端口契约一致（8081–8091）故互斥，
  由 `deployment/lib-mode-guard.sh` 双向守卫。一份参数化 `Dockerfile` 服务 10 个模块，镜像内不跑 Maven。
  决策见 ADR-0070（**Supersedes ADR-0057「服务未容器化」**）。
- **全链路自动化测试（新增 `deployment/e2e-tests` 模块）**：黑盒、不依赖业务模块。沉淀 9 条资金不变量断言原语
  （超退守卫 / 单号链 / 记账平衡 / 权益撤销 / 履约终止 / 库存守恒 / 幂等重放 / 无孤儿 …），
  支持确定性故障注入（金额尾数 11=超时 / 12=无结论 / 15=业务拒绝）。决策见 ADR-0069。
- **退款链路重构为两层退款单**：order 库 `transaction_refunds`（TXRF）与 payment 库 `refunds`（PMRF）**双号互记**；
  渠道退款改「受理 + 延迟推送」异步模式，回调带 HMAC 验签防重放，三路收敛到同一编排。决策见 ADR-0067。
- **可观测性补齐**：全服务统一单行 `ACCESS_LOG`（含服务名、耗时、报文），4 个调度器入口补 traceId，
  配套 `tail-logs.sh` / `trace-grep.sh <traceId>`；9 服务统一优雅停机 30s drain。决策见 ADR-0068。
- **数据模型规范化**：22 张表列序归一，新增 `order_item_no`（OI+雪花），履约由订单级**细化到明细级**，
  `payment_attempts` 补金额与币种留痕。决策见 ADR-0066。

## 新增

- **容器化运行栈**（spec 026）：`docker-compose.yml` 增 `pay-arch` 网络与 `infra` / `full` 两个 profile；
  应用 `depends_on nacos: condition: service_healthy`；应用日志靠 Dockerfile `tee` 双写落挂载卷
  （项目 logback 仅 CONSOLE appender，`logging.file.name` 无效）。
- **E2E 门禁**：`e2e.yml` nightly + 手动触发 + **v* tag 强制**；`verify.yml` 新增 `contract-snapshot` job，
  API 契约漂移 PR 即红，不等 nightly。
- **统一访问日志**：`AccessLogFilter`（common-core）每请求落一条 `ACCESS_LOG`，异常路径 try/finally 必打；
  `MdcTaskDecorator` + `TraceContext.runWithNewTrace()` 修复异步链路断 traceId。
- **两层退款单与退款回调**：order 侧新增 `transaction_refunds`；payment 侧新增渠道退款回调端点
  （HMAC 验签），`RefundResultProcessor` 三路收敛（同步受理 / 渠道回调 / 人工 resolve）。
- **演示门户与设计系统**：新增 `portal.html` 五类入口（演示 / 对账 / Grafana / Prometheus / 压测）；
  新增 `docs/design/DESIGN.md` + `static/design.css` 共享 token 层，4 个演示页视觉统一（零 CDN / webfont / npm）。
- **发行包形态**：`payment-platform-2.0.0-bin.tar.gz`（10 个 fat jar + 一键启停 + 建表 SQL + 演示场景 + k6 压测），
  目标机器只需 **JDK 21 + Docker**。

## 变更

- **编排归属收口（ADR-0054 延伸）**：退款的业务下游扇出（履约终止 / 权益撤销 / 秒杀回补）统一归 order 侧，
  payment 侧删除 `RefundPostProcessOrchestrator` 及 fulfillment / entitlement 直调。
- **资金口径补齐**：`transactions` 加 `payment_no`（生效支付单，首张成功写入不覆盖）与 `refunded_minor`（累计已退）；
  `OrderStatus` 补 `PARTIALLY_REFUNDED` / `REFUNDED`。
- **事务收窄**：`onPaymentSucceeded` 的出站 RPC（confirmStock / 履约）移出事务边界，改 TransactionTemplate 编程式事务；
  confirm 失败仅告警 + 指标，**不回滚 PAID**（事实不回滚）。
- **迁移脚本幂等化**：`018-schema-normalization.sql` 用 information_schema 守卫 + PREPARE 动态 SQL，存量库可重复执行。

## 修复

- **容器模式收银台 payUrl 客户端不可达**：compose 曾把 `mock-cashier.base-url` 配成容器内服务名，
  该值被拼进 `payUrl` 交给浏览器打开 → 宿主 NXDOMAIN。改用 `localhost:8091`；新增 `CashierPayUrlReachabilityTest`
  按绝对 URL 直连断言（已做有效性验证：改回错误值用例立刻变红）。
- `DemoProxyController` 对 payUrl 做兜底改写，即使环境变量再配错，/demo 页拿到的链接也可用。
- `Dump.write` 文件名未净化（step 含完整 URL 时写盘失败，恰恰丢掉诊断产物）。
- `scenario-refund.sh` 幂等键写死导致重跑命中重放、污染断言；两处全角括号吞变量。
- Prometheus 删除死目标 `refund`（:8085 已随 ADR-0064 退役）。
- 记账幂等键统一 `REFUND:{PMRF}`（修双重前缀）；`PaymentResultProcessor` 订单通知失败不再静默吞。

## ⚠️ 破坏性变更与升级步骤

从 v1.0.0 升级**必须**执行迁移脚本，否则退款与履约链路会异常。

1. **停栈**：`bash deployment/stop-all.sh`（宿主模式）或 `docker compose down`（容器模式）。
2. **执行迁移**（幂等，可重复执行；建议先备份）：
   ```bash
   mysql -u root -p < deployment/schema/018-schema-normalization.sql
   mysql -u root -p < deployment/schema/019-order-driven-refund.sql
   ```
3. **起栈**：宿主模式 `bash deployment/start-all.sh`，或容器模式 `bash deployment/start-container.sh`。

不兼容项清单：

| 项 | v1.0.0 | v2.0.0 |
|---|---|---|
| 退款创建入口 | `POST /internal/refunds` | **已删除**，改走 order 侧入口（人工 `resolve` 保留） |
| `refunds.refund_no` 前缀 | `RF` | `PMRF`（存量 `RF` 仍可读） |
| `fulfillments.order_item_id` | 订单级 | **明细级**（存 `order_item_no`，OI 前缀） |
| `GET /fulfillments/by-order` | 单个对象 | **返回数组** |
| 表列序 | 各表不一 | 统一「自增 id → 业务主键 → 唯一索引列 → 业务列 → 审计列」 |
| `payment_attempts` | 无金额 | 新增 `amount_minor` / `currency_code` |

## 已知问题

- **对账 `MISSING_POSTING` 本地伪影**：本机透明代理吞写所致，经 general_log / 访问日志 / 无沙箱复跑三重实证，
  CI 环境为准。
- **容器模式吞吐低于宿主**：容器堆 256m < 宿主 384m，叠加 NAT 开销，属预期取舍，非缺陷。
- **容器镜像构建依赖 Docker Hub**：网络不可达时 `docker compose build` 会失败，此时请用宿主模式。
- **spec 027 / 028 仅立项**：限额与渠道路由均未实现，ADR 为 Proposed，需负责人核准后开工。
