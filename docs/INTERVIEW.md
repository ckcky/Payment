# PaymentArch — 项目介绍（面试展示版）

> 定位：**面向生产环境形态的电商支付中台**，用 **AI 驱动的 Spec-Driven 工作流**从零构建。
> 不是 CRUD Demo：完整跑通「订单 → 支付 → 履约 → 权益 → 记账 → 对账 → 结算 → 退款」的**资金闭环**，并把每一次架构决策写成可追溯的 ADR，把每一条链路都配上自动化测试。
> 本文用于面试讲解：**怎么做的 / 做了什么 / 自动化到什么程度 / 难点在哪 / 亮点在哪**。

---

## 0. 电梯陈述（60 秒版）

> 这是一个 Java 21 + Spring Boot 3.5 + Spring Cloud 的支付中台，9 个微服务 + 1 个演示控制台，**27 张表、约 2.55 万行主代码、450+ 自动化测试**。
>
> 它有两个我想重点讲的差异点：
>
> **第一，开发方式。** 整个项目是我**用 AI 结对、按 Spec-Driven 流水线**做出来的：先立宪法和硬红线，再为每个特性走 Spec → Plan → Task → 分支实现 → 回检 → ADR → 合并；**24 个 Feature 规格、69 条架构决策**全部落文，包括被否决和主动「不做」的。我的角色是**需求取舍、架构决策、验收判断与审计**，AI 负责在约束下执行。为了让 AI 不失控，我写了项目宪法：9 条 AI 行为红线 + 8 类「人类决策边界」（领域边界、资金表迁移、状态机变更等 AI 只能提议、不得自行执行）。
>
> **第二，工程化程度。** 项目里「能自动的都自动了」：一键起栈、一键跑全场景、DDL 幂等迁移、4 个后台调度器自动收敛异常态、3 条 CI 流水线（PR 快跑 / nightly 全链路 / 发版）、架构边界用 ArchUnit 自动门禁、还有一个**独立的黑盒全链路 E2E 测试模块**——它能在真实栈上自动验证「退款对不对、超退拦不拦得住、对账准不准、单号记没记错」，失败自动落盘诊断包。
>
> 技术上我重点解决的是**钱不能错**：防超退、防重复扣款、账务借贷平衡、对账差异可检出可闭环，以及在没有 MQ 的前提下把跨服务最终一致性兜住。

## 1. 开发方式：AI 驱动的 Spec-Driven 工作流（最大差异点）

### 1.1 流水线（每个特性一条，AI 与人类分工明确）

```
Spec（写清"要什么"和"为什么"）        ← 人类定需求边界与验收，AI 起草
  → Plan（拆服务、定依赖顺序、识风险）  ← AI 出方案，人类拍板
    → Task（最小可执行任务，粒度=一次可独立验证的提交）
      → Branch（feature/<NNN>-<slug>，纯文档豁免）
        → Implement（逐任务实现 + 补测试）   ← AI 执行
          → Review（对照 Spec 回检缺口，补 ADR/文档）  ← 人类验收
            → PR & Merge（--no-ff 合并回 master）
```

**Spec 是需求的单一事实源**：没有 Spec 不写实现。Feature 开发的唯一入口是 Spec Kit（`.specify/`），不另起一套流程。

### 1.2 约束 AI 的三层机制（这是我真正的方法论产出）

| 层 | 内容 | 作用 |
|---|---|---|
| **① 项目宪法** `.specify/memory/constitution.md`（v2.3.0） | 领域边界、依赖方向、一致性、工程、可观测、**AI 原则**、人类决策边界、提交节奏 | 一切设计与实现的上位约束，AI 任何工作前必读 |
| **② AI 行为红线（9 条）** | 不得绕过架构规则 / 不得改无关代码 / **不得删测试解决失败** / **不得改测试迎合错误实现** / 不得擅改领域模型 / 重大变更先提方案 / 需求不明先澄清 / 实现前必须读懂现有代码 / 完成后必须测试与回检 | 防止 AI「图省事」式实现，这是协作中最常见的失控点 |
| **③ 人类决策边界（8 类）** | 领域边界调整、重大架构变化、资金表迁移、API 破坏性变更、安全策略、生产部署策略、数据迁移、**支付状态机变更** | AI 只能提出方案（含 A/B/推荐/风险），**必须我确认后才能执行** |

补充约束：金额禁用 `float/double`；资金变动必须走 ledger 复式记账；未知状态不猜成败；禁止引入 2PC/XA。

### 1.3 这套方式的产出证据（可当场打开）

| 证据 | 数量 | 位置 |
|---|---|---|
| Feature 规格（spec / plan / tasks / acceptance 四件套） | **24 个** | `docs/specs/<NNN-*/>` |
| 架构决策记录 ADR（含备选与否决理由） | **69 条 / 31 个文档** | `docs/adr/` |
| 明确记录为 **Rejected / Not Implemented** 的决策 | ADR-0016（部分退款，代码已回退）、ADR-0031（不用 MQ）、ADR-0027（脱敏）、ADR-0028（风控）、ADR-0034~0037（鉴权令牌） | `docs/adr/README.md` |

| 每服务系统设计文档 | 10 份 | `docs/architecture/systems/` |

> **面试话术**：我不把 AI 当代码生成器，而是把它当**受约束的执行者**——先立规则与边界，再用 Spec 驱动，最后用测试与 ADR 回检。副作用是项目天然留下了完整的决策链路，任何人都能回答「为什么这么做」。

## 3. 这个系统到底做了什么（业务闭环）

```
                    ┌─────────────── 正向：钱进来 ───────────────┐

  用户下单 ──▶ order（OR + 幂等键）──▶ 建交易（TR）──▶ 选渠道建支付单（PM）
                                                            │
                                                            ▼
                                              payment ──▶ 渠道尝试（PA 流水）
                                                            │ 渠道异步回调
                                                            ▼
                                   支付成功 ──▶ ledger 复式记账（PAYMENT/PM）
                                                            │
                    ┌───────────────────────┬───────────────┼───────────────┐
                    ▼                       ▼               ▼               ▼
              履约（按明细）            权益授予        订单置 PAID     库存确认
                    └───────────────────────┴───────────────┴───────────────┘
                                                            ▼
                              渠道对账（CSV）  +  会计四核对（账证/账账/账实/账表）
                                                            ▼
                                              结算批次（对账未收口则门禁拒绝）

                    └─────────────── 逆向：钱出去 ───────────────┘

  order 发起退款 ──▶ 交易层退款单（TXRF）──▶ payment 执行单（PMRF）──▶ 渠道退款 + 异步回调
                                                            │
                        ┌───────────────────────────────────┼───────────────────────┐
                        ▼                                   ▼                       ▼
                 ledger 冲正分录                   订单/交易状态流转        履约终止 → 权益撤销
                        └───────────────────────────────────┼───────────────────────┘
                                                            ▼
                                              秒杀商品回补库存（普通商品不回补）
```

**一句话概括能力边界**：正向走得通、逆向退得回、账务记得平、对账对得出、结算有门禁、全程可观测、全链路有自动化测试兜底。

## 6. 难点在哪（面试主战场）

> 每个难点按 **问题 → 约束 → 方案 → 证据/结果** 讲。

### 难点 1：没有 MQ（也没有 Outbox），怎么做跨服务最终一致性

- **问题**：支付成功后要驱动履约、权益、记账、订单状态；退款成功后要冲正账务、终止履约、撤销权益、回补库存。任何一步失败都会造成「钱收了、货没发 / 钱退了、权益没撤」。
- **约束（先说清现实，避免夸大）**：ADR-0031 明确**不使用 MQ**；`common-core` 也明确**不提供跨服务事件或 Outbox 机制**（Constitution §IV / plan §5）。所以最终一致性**完全靠同步调用 + 重试 + 幂等 + 落库留痕**兜。
- **方案**：
  1. **出站端口抽象为 Gateway 接口 + Feign 实现**（`PaymentGateway` / `FulfillmentGateway` / `LedgerPostingGateway` / `EntitlementGateway`），领域层只依赖接口，实现可替换、单测可 fake；
  2. **编排器顺序扇出 + 逐步重试 + 每步落库**：`RefundPostProcessOrchestrator` 按固定顺序执行后处理，**每步 3 次重试**，尝试记录落 `refund_post_process_attempts`；
  3. **事实不回滚原则**（ADR-0054）：已发生的资金事实（支付成功 / 退款成功）**不因下游失败而回滚**，改重试 + 补偿 + 告警，避免「本地回滚但远端副作用已发生」；
  4. **事务边界收窄**（spec 023）：出站 RPC（确认库存、驱动履约）移出事务边界，DB 段用 `TransactionTemplate`；confirm 失败仅告警并打 `order.stock_confirm_failed` 指标，不回滚 PAID；
  5. **每步幂等可重入**：下游按业务单号幂等，重复通知不产生重复分录 / 重复履约；
  6. 支付侧另有 `PaymentRetryService` 与定时查单自动收敛 UNKNOWN。
- **代价（诚实讲）**：没有 MQ 就缺少削峰与自动重投，长尾失败靠重试记录 + 告警 + 人工介入；重新评估引入异步通道的条件已写在 ADR 中。

### 难点 2：并发下防超退（钱不能多退一分）

- **问题**：同一笔支付多次部分退款，并发请求可能同时通过「累计已退 ≤ 实付」校验 → 超退。
- **方案（三道防线）**：
  1. **权威校验在支付层**（原单在支付层）：`RefundPolicy.decide()` 纯函数校验币种一致 / 金额 > 0 / `累计已退 + 本次 ≤ 实付`；
  2. **`refund_intake_locks` 悲观锁按 paymentNo 串行化**，且 **PROCESSING/UNKNOWN 在途单按申请额保守占用** —— 这是防并发超退的根本；
  3. **交易层第二道**：`transactions.refunded_minor` 累加 + `Order.recordRefund()` 超退校验（防御上游逻辑错误）。
- **结果**：E2E `OverRefundGuardE2ETest` 覆盖**单次超退 / 累计超退 / 并发竞态**三类，断言「成功总额恰等于可退额 + DB 侧 `refunded_minor ≤ paid_minor` 恒真」。

### 难点 3：在途态（UNKNOWN）的收敛与后处理不能丢

- **问题**：渠道返回「未知」时既不能当成功也不能当失败；且**同步成功、异步回调、人工 resolve** 三条路径若各写一套后处理，必然行为不一致。
- **方案**：支付侧定时查单自动收敛；退款侧保留 `resolve` 人工收敛（并明确**不建**自动收敛器，避免过度设计）；**三路收敛统一到同一后处理编排**；每步幂等可重入。
- **结果**：E2E 有专门用例断言「回调丢失 → UNKNOWN → resolve 收敛后，记账/权益/订单状态全部补齐」——最容易漏、也最容易被追问的一条。

### 难点 4：退款的两层单据模型（为什么不是一个单号走天下）

- **问题**：一个交易（TR）下可能有多笔支付单（PM），一笔支付单下可能有多笔退款；交易层必须留痕，支付层必须持有渠道事实。
- **方案**（对标国内中台双层单据 + 微信 `out_refund_no` + Stripe Refund 对象）：
  - 交易层生成 **TXRF+雪花** 退款单；支付层生成 **PMRF+雪花** 退款执行单；
  - **两层互记对方单号**（`transaction_refunds.payment_refund_no` ↔ `refunds.transaction_refund_no`）；
  - 交易层重试同 TXRF 可重入，支付层以 TXRF 为幂等键返回同一 PMRF；
  - **对账口径以支付层 PMRF + 渠道流水号为准**（渠道事实在支付层）。
- **结果**：多次退款 = 多个 TXRF ↔ 多个 PMRF 一一对应，交易层逐笔可查，单号链被 E2E `BusinessNoChainE2ETest` 断言。

### 难点 5：账务正确性与对账闭环

- **问题**：记账错了没人知道，对账只能靠人眼。
- **方案**：
  1. **复式记账 + 借贷平衡**：任何资金路径必经 ledger；分录 append-only；可按业务单号追溯；余额可从分录重算校验；
  2. **渠道对账**：渠道账单 CSV 与本地记录比对，检出长款 / 短款 / 金额不符 / 单边账 / 重复；
  3. **会计四核对**（spec 017）：账证 / 账账 / 账实（双轨）/ 账表，差异分 **8 类 × BLOCKER/MAJOR/MINOR**，走 **挂账 SUSPENSE → 调账（大额强制双人复核、操作人≠复核人）→ recheck → 关批**，未收口差异**拒绝结算**。
- **结果**：E2E 用「DB 直改注入 8 类差异 → 断言 100% 检出且分类正确 → 还原」与 CSV 渠道差异注入两组用例验证。

### 难点 6：秒杀与库存一致性

- **方案**：三段式库存（reserve / confirm / release）+ 预留表；**Redis Lua 原子预扣**（`seckill-deduct.lua`）；Redis ZSet 时间轮 + 调度器超时释放；退款时**仅秒杀商品回补**（普通商品不动）；限流 + 明确丢弃语义（ADR-0046）。
- **结果**：库存守恒被纳入 E2E 断言原语。

### 难点 7：让 AI 协作不失控（工程治理难点）

- **问题**：AI 生成速度快，最容易失控的是「为什么这么做」随时间丢失、代码先行导致文档漂移、以及 AI 为图省事删/改测试。
- **方案**：
  1. **宪法 + 红线 + 人类决策边界**（见 §1.2），把约束写进 AI 每次动手前必读的文件；
  2. **决策即资产**：任何决策写 ADR，**含备选方案与否决理由**；主动记录「不做」（ADR-0016 部分退款被 Rejected 且代码回退、ADR-0031 不用 MQ、安全能力保留桩并写明部署风险）；
  3. **ArchUnit 自动门禁**守服务边界；
  4. **审计与整改**：代码先行部分（013/014）事后补 spec 与 ADR 收口，并把这次偏离本身记录为 ADR-0053 作为教训；技术债集中登记在 `code-debt-backlog.md`；
  5. **文档漂移治理**：文档与代码同步纳入审计，本轮已修正 README 中「事务性 Outbox」「集成测试用 Testcontainers」两处与代码不符的漂移。

### 难点 8：全链路自动化测试本身（meta 难点）

- **问题**：E2E 天然慢、脆、难定位，容易沦为「演示脚本」。
- **方案**（spec 022）：
  1. 独立黑盒模块（HTTP + JDBC，不依赖业务代码），Awaitility 轮询（**禁用 sleep**）+ 失败自动 dump 诊断包；
  2. **行级断言复用 `/demo/trace`**（跨 9 库 14 表快照 API），**聚合不变量才直连 MySQL**，沉淀 9 条断言原语；
  3. **确定性故障注入**，不靠概率与等待；
  4. **识别并规避三个「假绿陷阱」**：渠道回调验签是占位恒放行（禁止据此写断言）、对账控制台 MOCK 模式纯前端（必须走 LIVE）、渠道对账差异来自固定 CSV（与真实链路无关，断言要拆两套）；
  5. **测试有效性反证**：故意注入缺陷（去掉累计校验 / 不回填 `payment_refund_no`），对应用例必须变红。

## 7. 亮点在哪（差异化，一句话一个钩子）

1. **AI 驱动的 Spec-Driven 开发方式**：宪法 + 9 条 AI 红线 + 8 类人类决策边界 + Spec/Plan/Task/回检流水线，24 个 Feature 规格、69 条 ADR 全链路可追溯——**展现的是工程管理能力，不只是写代码**。
2. **自动化覆盖到「验证」层面**：不只是起服务自动化，而是**正确性验证自动化**——独立 E2E 模块能在真实栈上自动判定「退款对不对、超退拦不拦得住、对账准不准、单号记没记错」，失败自动落盘；再加 ArchUnit 边界门禁、4 个自动收敛调度器、3 条 CI 流水线、幂等迁移、一键起栈/演示。
3. **资金闭环完整**：正向支付、逆向退款、复式记账、渠道对账、会计四核对、结算门禁，一条链走到底，不是只有「下单支付」的半成品。
4. **钱的安全性是设计出来的**：最小单位整数金额、两层金额校验、悲观锁串行化、在途保守占用、事实不回滚 + 补偿、分录 append-only + 借贷平衡断言。
5. **69 条 ADR 含「否决」与「不做」**：体现取舍能力而非堆功能——主动放弃 MQ、主动回退部分退款、安全模块保留桩并写清部署风险。
6. **两层退款单 + 统一雪花单号体系**：OR/TR/PM/PA/TXRF/PMRF 前缀 + 雪花，跨库互记可追溯，对账口径清晰。
7. **端到端可演示**：mock 渠道 + 收银台 + 演示控制台（全链路 DB 数据快照）+ 对账控制台（8 类差异可视化闭环）+ 门户页聚合 Grafana/Prometheus/压测入口，两条命令跑通。
8. **可观测不是摆设**：全链路 traceId（含异步与定时任务 MDC 传播）、统一 ACCESS 日志、Grafana 预置看板（含服务间 Feign RPC 面板）、日志聚合与 trace 检索脚本。

## 9. 高频追问与回答要点（提前准备）

| 追问 | 回答要点 |
|---|---|
| **这是 AI 写的吗？你的贡献是什么？** | 是 AI 结对，但分工明确：我负责需求取舍、领域边界、架构决策、验收判断与审计；AI 在宪法与红线约束下执行。69 条 ADR 每条都是我拍板（含否决与「不做」）；8 类人类决策边界 AI 只能提议、不得自行执行；我对 AI 产出做 Spec 回检、测试门禁与文档漂移审计（已修正 README 的 Outbox/Testcontainers 漂移）。 |
| AI 写代码你怎么保证质量？ | 三层机制：宪法 + 9 条红线（尤其"禁止删测试/改测试迎合错误实现"）+ 8 类人类决策边界；再加 ArchUnit 边界门禁、单服务 450+ 测试、E2E 黑盒验证与失败 dump；每个特性回检后再合并。 |
| 为什么不用 MQ？ | ADR-0031 明确记录：学习项目控制复杂度，改用同步 Feign + 编排器重试 + 幂等补偿；代价是无削峰与自动重投，长尾失败靠落库留痕 + 告警 + 人工，重新评估条件已写进 ADR。 |
| 分布式事务怎么处理？ | 不用 2PC，也没有 Outbox。本地事务只管本库；出站调用抽象成 Gateway 接口 + Feign，由编排器顺序扇出、逐步重试并落 `refund_post_process_attempts`；下游按业务单号幂等；**资金事实不回滚**（ADR-0054）。 |
| 怎么保证不超退？ | 三道防线：支付层权威校验、`refund_intake_locks` 串行化 + 在途保守占用、交易层第二道；E2E 有并发竞态用例。 |
| 为什么退款要两层单号？ | 交易层要留痕与重试幂等（TXRF），支付层要持有渠道事实（PMRF）；两层互记，对账以支付层为准。对标微信 `out_refund_no` 与国内中台双层单据。 |
| 对账发现差异怎么办？ | 8 类差异分类 → 挂账 SUSPENSE → 调账（大额强制双人复核）→ recheck → 关批；未收口则拒绝结算。 |
| 重复回调 / 乱序回调怎么办？ | 回调幂等（按业务单号与状态机吸收，终态不被回退），UNKNOWN 走收敛且后处理不丢。 |
| 项目最大不足 / 下一步？ | ① 鉴权、验签、脱敏、风控按裁决为桩实现（已写清部署风险与网络隔离要求）；② 部分退款语义与退款自动收敛器明确不做；③ Redis 引入未经压测论证闸门（已登记技术债）；④ E2E live 全量回归与 CI nightly 待实跑验证。 |
