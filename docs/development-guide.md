# 开发入口（Development Guide）

本文是项目日常开发的唯一入口。原则看 Constitution，具体特性看 `specs/<feature>/`，不要再为同一件事维护第二套流程文档。

## 一次特性如何完成

### 0. 先判断是不是 Feature

- 新增业务能力、接口、状态、表或跨服务协作：是 Feature，必须走 Spec Kit。
- 修复一个明确的局部缺陷：可直接修复，但仍需先读相关 Spec、测试和代码。
- 改变服务边界、支付状态机、关键资金表、已发布 API 或新增中间件：先写方案并等待人类确认。

### 1. 创建并确认需求

```text
/speckit-specify <用业务语言描述目标、用户、场景和约束>
```

检查 `specs/<feature>/spec.md`：范围是否小而明确，正常流、失败流、重复请求、超时和未知状态是否有验收标准。需要讨论的业务选择先解决，再进入设计。

### 2. 形成技术设计

```text
/speckit-clarify       # Spec 有关键歧义时才用
/speckit-plan
/speckit-analyze       # 需要跨文档一致性检查时用
```

Plan 阶段确认服务边界、数据所有权、状态变化、一致性、依赖、可观测和验证路径。重大决策另写 `docs/adr/`，不要把 ADR 内容重复塞进 Spec。

### 3. 生成任务并实现

```text
/speckit-tasks
/speckit-implement
```

先完成基础设施任务，再按用户故事逐步实现。每个任务都要能独立验证；测试、迁移、接口契约和文档不能被当成“以后再补”。

### 4. 回检与收尾

```text
/review
/payment-review       # 触及支付、退款、账本、对账、结算时
```

对照 Spec 验收，确认测试和 `quickstart.md` 可执行；未完成内容写入 Feature 文档或后续任务。不要用修改测试断言的方式掩盖实现问题。

## 哪些事情不用重复手写

Spec Kit 已负责模板、目录、计划附件、任务编号、依赖关系和质量清单。项目文档不再维护 `docs/specs/`、`docs/plans/` 或另一份任务表。

需要人工写或确认的仍然是：业务规则与范围、关键架构决策、支付状态机、数据迁移、安全策略、对外破坏性变更，以及最终验收。

## 推荐的首个开发顺序

当前仓库还没有业务代码和构建骨架，因此不要一开始创建全部微服务。建议按可运行的纵向切片推进：

1. **Bootstrap**：父 Maven 工程、一个可启动服务、统一错误处理、健康检查、基础测试和 README。
2. **Catalog → Order**：商品/SKU 查询和创建订单，先建立 API、数据库独占和订单状态机。
3. **Payment MVP**：使用 Mock Channel 完成支付意图、幂等、回调、UNKNOWN 状态和支付事件；先不接真实渠道。
4. **Fulfillment → Entitlement**：消费支付成功事件，验证 Outbox、幂等消费和权益发放。
5. **Ledger**：在真实资金动作前建立复式记账模型和不变量测试。
6. **Refund**：在支付、账本、履约/权益已有边界后实现退款编排。
7. **Reconciliation → Settlement**：先对账发现差异，再做基于已确认数据的结算。

每一步只创建当前 Feature 需要的模块。新增服务、中间件、关键资金表或生产部署策略都必须回到 Constitution 的人类决策边界。

## 当前阶段的完成定义

文档阶段完成的标志不是“目录齐全”，而是：项目目标和边界明确、第一条纵向切片已选定、Feature Spec 能验收、技术方案无未决重大决策、任务可以直接执行。完成这些后，再创建 Maven 骨架并运行第一条可重复的构建命令。
