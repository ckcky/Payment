# 服务 / 数据库拆分提案模板

**用途**：Phase 10（分布式演进）的准入门禁。任何一次服务拆分、数据库实例拆分、或引入新的分布式基础设施（MQ / 容器编排 / Service Mesh），**必须先填完本模板并通过负责人评审**。

**依据**：`docs/adr/0010-distributed-evolution-decisions.md`（ADR-0029~0033）；Roadmap Phase 10「不因『看起来像微服务』而默认引入…」；Constitution §8 人类决策边界（服务边界、领域边界、Schema 变更 MUST 由人确认）。

**四段必填，缺一不予评审**：问题（证据） → 收益 → 成本 → 回滚方案。

- 涉及服务：
- 关键等级（T0~T3，见 ADR-0032）：
- 关联的 ADR：（新增或修订的 ADR 编号）

## 1. 问题（必须有证据）

> 不允许以「看起来该拆了」「微服务就该这样」作为理由。必须给出可观测证据。

- **观察到的现象**：（哪个指标、什么时间窗、数值是多少）
- **证据来源**：（Prometheus 指标 / 慢查询日志 / 压测报告 / 故障复盘；附链接或截图）
- **根因分析**：（为什么当前形态解决不了？为什么不是配置问题或代码问题？）
- **触发了哪条 ADR-0030 条件**：（容量 / 隔离 / 合规归属 / 可用性）
- **已排除的更廉价方案**：（垂直扩容？索引优化？跑批错峰？超时与熔断参数调整？缓存？）——**必须逐条说明为什么不够**

## 2. 收益

- **量化收益**：（预计 P99 从 X 降到 Y、连接数下降多少、故障域缩小到什么范围）
- **定性收益**：（独立发布节奏、团队 ownership 清晰、合规边界成立）
- **验证方式**：（上线后看哪些指标、观察多久、达到什么阈值算成功、达不到怎么办）

## 3. 成本

- **运维成本**：（新增几个实例 / 几套备份 / 几条监控告警 / 谁 oncall）
- **一致性成本**：（是否引入跨库事务？是否引入最终一致？对账与补偿链路怎么改？）
- **开发成本**：（代码改动范围、是否需要双写期、预计工期）
- **风险**：（数据迁移丢数的可能性、双写不一致窗口、回滚复杂度）
- **对现有契约的影响**：（是否涉及 `common-dto` RPC DTO 变更？见下方兼容性检查）

## 4. 回滚方案

- **回滚粒度**：（按 Schema 粒度切流？按服务实例回滚？）
- **双写期安排**：（双写持续多久、以哪一侧为权威、如何校验两侧一致）
- **回滚判据**：（出现什么指标或现象就回滚）
- **回滚步骤**：（1..N，可直接执行的具体命令与操作顺序）
- **回滚窗口**：（多久内可完成回滚；超时怎么办）
- **账本特别说明**：（若涉及 `ledger-service`：回滚前如何确认没有新 Posting 产生；是否用补偿分录而非删数据）

## 5. 契约兼容性检查（必答）

- [ ] 现有跨服务契约（`common-dto` 的 RPC DTO）保持向后兼容
- [ ] 若有破坏性变更，已提供新端点 + 双轨期，未就地改语义
- [ ] 所有跨服务调用方仍只经 HTTP/Feign + `common-dto`，未引入跨服务编译期依赖
- [ ] `architecture-tests` 的结构规则仍然通过（服务零耦合 / domain 框架无关 / 接入层不直达仓储 / 无 MQ-JTA）
- [ ] 运行手册 `docs/operations/runbook.md` 已同步更新（端口、依赖、故障处置、回滚）
