## 2. 设计原则（先立规矩，再谈方案）

1. **Demo 不等于玩具**。宪章 Core Principle I 明确「Production-Oriented，不是 Demo」。因此演示的定位是：
   **真实链路 + 确定性可控的外部环境 + 一键复现脚本 + 可视化**。
   演示脚本只做**编排与展示**，**MUST NOT** 直接写业务状态、跳过状态机或伪造事实。
2. **Redis 不是真相源**。任何时刻 Redis 数据可全部丢失，系统仍**正确**（只是变慢）。资金判定、库存终扣、权益发放、记账 MUST 以 DB / Ledger 为准。
3. **正确性先于性能**。幂等的兜底 MUST 落在 DB 唯一约束，Redis 去重窗口只是加速器，不是保证。
4. **引入中间件必须有证据**。宪章 IV.6 + `010-distributed-evolution` 闸门：**先压测拿证据 → 填 `split-proposal-template.md` 四段 → ADR 五问论证 → 再引入**。顺序不可颠倒。

## 4. F1 — `011-demo-showcase`：让链路"看得见"

### 4.1 Mock 收银台（把"跳转三方渠道"变成真的）

当前 `MockChannelAdapter` 在进程内直接返回结果，演示时看不到"跳转"这个动作。设计：

```text
前端/脚本                    payment-service              mock-channel-web（新）
   │  POST /payments          │                              │
   ├─────────────────────────>│                              │
   │   ← { paymentId, payUrl }│                              │
   │                          │                              │
   │ 浏览器打开 payUrl ───────────────────────────────────────>│  收银台页面
   │                          │                              │  商品/金额/倒计时
   │                          │   用户点「成功/失败/超时/无结论」│
   │                          │<─── POST /payments/{id}/channel-callback（带 HMAC 签名）
   │                          │                              │
   │  轮询 / 前端刷新 ────────>│ 状态：PAID / FAILED / UNKNOWN │
```

- 收银台是**独立最小 Web（纯 HTML + 一个回调转发接口）**，不引入前端框架。
- 回调走**已有**的 `ChannelCallbackController` + `ChannelCallbackSignatureFilter`（009 已落地签名与防重放），不另起炉灶。
- **设计要求**：收银台必须支持四种"坏行为"，这是演示的真正价值：

| 操作 | 演示的正确性问题 |
|---|---|
| 连点两次「支付成功」 | 重复回调 → 幂等吸收，不重复入账、不重复发权益 |
| 改金额后伪造回调 | 签名校验拒绝（已有能力，可现场验证） |
| 点了不回调（直接关页面） | Payment 进 UNKNOWN → `ChannelQueryScheduler` 主动查询收敛 |
| 选「渠道无结论」 | 进 UNKNOWN，显式拒绝"猜成败落账"（宪章 V.7） |

### 4.2 演示编排脚本（`demo/` 目录，新增）

| 文件 | 职责 |
|---|---|
| `demo/seed.sql` | 种子数据：1 商户、2 商品、3 SKU（含 1 个秒杀 SKU），幂等可重复执行 |
| `demo/reset.sh` | 清库 + 灌种子，保证"每次演示从同一个确定状态开始" |
| `demo/scenario-happy-path.sh` | 建单 → 拿 payUrl → 回调 → 断言权益 AVAILABLE → 打印 Grafana 关注点 |
| `demo/scenario-payment-unknown.sh` | 不回调 → 观察 UNKNOWN → 主动查询收敛 → 最终一致 |
| `demo/scenario-refund.sh` | 全额 / 部分退款 → 断言累计退款不超限、权益撤销 |
| `demo/scenario-reconciliation.sh` | 制造 4 类差异 → 跑 T-1 对账 → 查差异 → 处理 → 关闭 |

**脚本纪律**：每步打印 `curl` 命令 + 响应摘要 + 下一步提示；末尾 MUST 有**断言**（而非仅打印），失败非零退出。

### 4.3 对账演示的前置修复（真实的既有缺陷）

对账要能"每日"演示，必须先修两处（已有 ADR-0019 登记，非本次新发现）：

1. `beginProcessing()` / `close()` 未被调用 → batch 停在 `HAS_DIFFERENCE` 后无法推进，"处理中→关闭"演不出来。
2. `CsvChannelStatementLoader.load(period)` 忽略 `period` 入参 → "每日对账"实际是假的（永远同一份 fixture）。

修复后，对账演示才能真实呈现：**按 T-1 period 取账单 → 匹配 → 4 类差异 → 处理 → 关闭**。

## 5. F2 — `012-entry-idempotency`：用户点两次下单怎么办

### 5.1 分层防御（明确每层"防得住什么、防不住什么"）

| 层 | 手段 | 防住 | **防不住** |
|---|---|---|---|
| L0 客户端 | 按钮置灰 / loading / debounce | 手抖双击 | 刷新、后退、多标签、脚本、网关重试、网络重传 |
| L1 前端幂等键 | 进入下单页向服务端申请 `Idempotency-Key`，重复提交带同一 key | 同页面重复提交（含刷新/多标签） | 换设备、key 过期后重下、用户真想买两件 |
| L2 接入层去重窗口 | Redis `SETNX` + 短 TTL（**014 引入，可选增强**） | 真正的并发重复 | Redis 不可用（必须降级到 L3） |
| L3 **服务端 DB 唯一约束** | `uk(idempotency_key)` | **唯一真正的兜底** | 无 key 的老客户端 |
| L4 业务弱提示 | 同用户 + 同 SKU + 短窗内有待支付单 → 提示 | 体验问题 | 不能当正确性保证 |

> **核心结论（面试高分点）**：前端只能**减少重复发生**，**不能保证不发生**。正确性兜底 MUST 在服务端 DB 唯一约束——因为 L0~L2 每一层都能被绕过（禁用 JS、换设备、并发、缓存失效），而 DB 唯一约束不会。

### 5.2 并发下的关键难点：不能"先查再建"

`先 SELECT 有没有 → 没有则 INSERT` 存在 TOCTOU 竞态，两个并发请求会同时通过检查。正确设计是**先占坑**：

```text
1. INSERT INTO order_idempotency_keys(key, status='IN_PROGRESS', expire_at) 
   → 成功：获得执行权，继续建单，回填 order_id，status='DONE'
   → 撞唯一键：说明已有请求在/曾处理，回查该行
2. 回查分支：
   - DONE         → 返回首次响应（200，同 orderId）
   - IN_PROGRESS 且未过期 → 409「处理中」+ 建议客户端轮询
   - IN_PROGRESS 但已过期 → 允许 CAS 接管（见下）
```

**"超时接管"是个必须显式设计的坑**：原请求可能仍在进行（只是慢），接管会导致双写。
建议策略（写入 ADR）：
- 首选：**不接管**，让客户端轮询首个请求（语义最清晰，生产更稳）；
- 若必须接管：`UPDATE ... WHERE key=? AND status='IN_PROGRESS' AND expire_at < now()` 靠影响行数抢锁，且原请求在写结果前 MUST 再次校验自己仍是持锁者（双重检查）。

### 5.3 三条容易漏的细则

1. **响应必须可重放**：重复请求返回**与首次完全一致**的响应（含同一个 `orderId`）。否则前端会拿到两个"不同"的结果，比重复建单还难排查。→ 幂等记录需存 orderId 并重建响应，或存响应快照。
2. **幂等键用 HTTP 头**：`Idempotency-Key`（Stripe 等工业实践），不塞 body，便于网关统一处理。
3. **三把锁要分开讲，别混为一谈**：
   - **下单幂等**：一个 key 一张单（本次解决）
   - **支付幂等**：一个 orderId 只能有一笔有效 Payment（Payment 已有幂等，但 order→payment 的创建是否幂等需核实）
   - **库存扣减幂等**：一次扣减一个 `deductId` 幂等（013 解决）

## 6. F3 — `013-inventory-reservation`：库存域与预占模型

### 6.1 归属决策（要立 ADR）

库存放哪？三条路：① catalog 内新增 `Stock` 聚合 ② 独立 `inventory-service` ③ order 内。
**推荐 ①**：库存是 SKU 的销售属性，与商品同属一个 Bounded Context；宪章 IV 禁止「无理由新增微服务」，过早拆分是复杂度炫技。

### 6.2 三段式库存与铁律

```text
total = available + reserved + sold
```

任何变更必须三者**同增同减**（本地事务 + 行锁/乐观锁版本），禁止只改一个字段。

| 阶段 | 动作 | 变更 |
|---|---|---|
| 下单 | 预占 reserve | `available -= n; reserved += n` |
| 支付成功 | 确认 confirm | `reserved -= n; sold += n` |
| 支付失败 / 超时关单 | 释放 release | `reserved -= n; available += n` |

### 6.3 超卖的三道防线

1. **DB 层（最后防线，永不超卖）**：`UPDATE stock SET available = available - ? WHERE sku_id = ? AND available >= ?`，**靠影响行数判定成功与否**——原子条件更新，不存在检查与写入之间的窗口。
2. **Redis 层（014）**：Lua 脚本保证"判断 + 扣减"原子，把 99% 流量挡在 DB 前。
3. **对账兜底**：定期对 `sold + reserved` 与订单/支付事实核对，不一致则告警。**这里能把新能力与已有对账能力串起来**，是很漂亮的设计闭环。

### 6.4 与已有能力的衔接

- 订单超时释放库存：可复用 payment-service 已有的 `TimeoutScanner` 模式（DB 扫描），也可选 Redis ZSet 延迟队列——两者对比需写 ADR（宪章禁 MQ，RocketMQ 延迟消息不在选项内）。
- 释放失败 MUST 可重试且幂等（`release` 带 `deductId` 幂等键）。

## 7. F4 — `014-seckill-and-cache`：压测 → 论证 → 引入

### 7.1 顺序不可颠倒

```text
① 压测基线（无 Redis）→ 拿到真实瓶颈证据（P99 / 拐点 / 热点行）
② 填 docs/operations/split-proposal-template.md（问题-证据 / 收益 / 成本 / 回滚）
③ ADR 论证宪章 IV.6 五问
④ 才引入 Redis，且限定用途边界
⑤ 再压测，前后对比，报告进 docs/perf/
```

> 这个顺序本身就是亮点：**不是先上 Redis 再找场景，是先压测拿到证据再决定要不要上。**

### 7.2 Redis 引入的宪章五问（IV.6 门槛，逐条回答）

| # | 问题 | 回答 |
|---|---|---|
| ① | 解决什么问题 | 秒杀下商品详情读放大；库存热点行成为 DB 写瓶颈；多实例部署时本地内存去重失效 |
| ② | 为何当前方案不行 | DB 唯一约束能保证**正确**但挡不住**流量**（热点行行锁排队 → P99 劣化）；单机本地缓存在多实例下无效 |
| ③ | 收益 | 读 QPS 提升、DB 热点行压力下降、秒杀承载并发数量级提升 |
| ④ | 成本 | 新增中间件（compose 加容器）；缓存三件套（穿透/击穿/雪崩）需处理；本地开发多一依赖；集成测试需 Testcontainers 或 embedded Redis |
| ⑤ | 长期维护 | Redis 为标准件，学习/运维成本低，可控 |

**用途边界（写死，不可越界）**：仅用于 **缓存 / 去重窗口 / 库存预扣计数 / 限流**。
**MUST NOT** 用作：持久化真相源、消息通道、资金判定依据、权益发放依据。

### 7.3 Redis 用法与对应风险

| 用途 | 结构 | 收益 | 风险与对策 |
|---|---|---|---|
| SKU 详情缓存 | String/Hash + TTL | 挡读流量 | Cache-Aside + 更新即删；短 TTL；不强一致 |
| 幂等去重窗口 | `SETNX` + TTL | 并发重复挡在 DB 前 | **Redis 挂了必须降级到 DB 唯一约束**，不能只靠它 |
| 秒杀库存预扣 | Lua 原子 `DECR` | DB 压力下降 | Redis 与 DB 不一致 → 需"预扣对账 + 回补" |
| 分布式锁 | Redisson（**能不用就不用**） | 防重复扣减 | 锁过期而业务未完 → 看门狗续期；优先用原子操作代替锁 |
| 限流 | 令牌桶 / 滑动窗口（Lua） | 秒杀入口削峰 | 误杀需可观测与可关闭 |

**缓存三件套（必答）**：
- **穿透**：空值缓存 + 参数校验（非法 skuId 直接拒）；量大可加布隆过滤器
- **击穿**：热点 key 逻辑过期 + 互斥重建（不设物理过期）
- **雪崩**：TTL 随机抖动 + 多级缓存 + 熔断降级

### 7.4 红线（写进设计，也是面试亮点）

> **Redis 预扣成功 ≠ 扣减成功，只是"获得了去 DB 扣减的资格"。**
> 最终扣减 MUST 以 DB 条件更新为准。权益发放、记账 MUST 走 DB + Ledger，不经过 Redis 判定。
> 任何时候清空 Redis，系统仍正确，只是变慢。

### 7.5 压测方案

**工具选型**：推荐 **k6**（脚本即代码、易版本化与 CI 集成、可输出 Prometheus）。备选 Gatling（Java 栈契合）、JMeter（GUI 友好）。

**三个层次**：

| 层次 | 场景 | 关注指标 |
|---|---|---|
| 单接口基线 | `GET /skus/{id}`、`POST /orders` 逐步加压 | P50/P95/P99、拐点、错误率 |
| 链路压测 | 下单→支付→回调 混合场景（带 think time） | 端到端 P99、各服务耗时占比 |
| 秒杀脉冲 | 库存 100 / 并发 5000 瞬时到达 | **不超卖**、不漏卖、无重复单、限流生效 |

**压测纪律（真实项目容易踩的坑，必须写）**：
1. 环境隔离：独立 schema + 独立 seed，压测数据一键清理。
2. **识别定时任务干扰**：`TimeoutScanner` / `ChannelQueryScheduler` 会与压测抢 DB，需记录其频率并可临时关闭。
3. **声明 Mock 通道场景**：`MockChannelAdapter` 的 `httpTimeoutMs=1500` 会人为拉低吞吐，报告中 MUST 注明所用场景。
4. 指标采集：压测期间抓 `/actuator/prometheus`（已有），对比 DB 连接池、GC、错误率。
5. **报告入库**：`docs/perf/baseline-*.md`，作为 Redis 引入的证据链。

**秒杀断言**（可自动化）：`sum(sold) == 100`、`sold == 成功订单数`、`sold + reserved + available == total`、无重复 orderId。

| 3 | **超时 ≠ 失败**，进 UNKNOWN | ✅ `TimeoutScanner` + `ChannelQueryService` | 讲"MUST NOT 猜成败落账" |
| 4 | **重复回调 / 重复消息** | ✅ 幂等键 + 状态机吸收 | 011 收银台可现场演示 |
| 5 | **掉单 / 单边账** | ✅ 主动查询 + 对账兜底 | 演示：不回调 → UNKNOWN → 收敛 |
| 6 | **超卖** | ❌ 无库存 | 013 补齐；三道防线 |
| 7 | **价格不信前端** | ⚠️ 有 `SkuSnapshot` 待核实 | 服务端 MUST 以 SKU 现价/快照重算并校验总价 |
| 8 | **重复支付**（多标签页各付一次） | ⚠️ 待核实 | 需"支付单唯一 + 重复支付自动退款"路径 |
| 9 | **对账差异与长短款** | ✅ 4 类差异 | 可补"挂账处理" |
| 10 | **退款并发**（退款 vs 支付回调同时到） | ✅ 悲观 + 乐观锁 | 可现场演示 |
| 11 | **资金只追加不修改**，更正用冲正 | ✅ Ledger 复式记账 | 讲 append-only + 借贷平衡 |
